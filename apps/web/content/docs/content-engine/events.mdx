Each content type emits events named `content.<id>.<action>` after a change, such as `content.newsroom.story.published`. Subscribe to them to send a newsletter, sync an external index or purge a CDN, without touching the code that made the change.

Events come from the generated routes, scheduled publishing and [`contentEditorialEffects`](/docs/content-engine/services#save-like-the-admincp). The plain `service(c)` emits nothing. A save that changes nothing emits nothing either.

## Event reference

Which events exist depends on what the definition enables. `newsroom.category` declares only fields and emits three. `newsroom.story` has publication, editorial with scheduling and delivery, and emits ten.

| Action                      | Payload                                                                                         | Needs                          |
| --------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------ |
| `created`                   | `{ contentId, duplicatedFromId? }`                                                              | always                         |
| `updated`                   | `{ contentId, changedFields }`                                                                  | always                         |
| `deleted`                   | `{ contentId }`                                                                                 | always                         |
| `published`                 | `{ contentId, publishedAt, scheduledBy?, scheduleId? }`                                         | `publication`                  |
| `unpublished`               | `{ contentId, scheduledBy?, scheduleId? }`                                                      | `publication`                  |
| `restored`                  | `{ contentId, changedFields, version, revisionId, restoredFromRevisionId }`                     | `editorial`                    |
| `scheduled`                 | `{ contentId, action, actorUserId, scheduledFor, scheduleId }`                                  | `editorial.scheduling`         |
| `schedule_cancelled`        | `{ contentId, action, actorUserId, scheduleId }`                                                | `editorial.scheduling`         |
| `translation_created`       | `{ contentId, locale, languageId, version, revisionId? }`                                       | `localization`                 |
| `translation_updated`       | `{ contentId, locale, languageId, version, changedFields, revisionId? }`                        | `localization`                 |
| `translation_deleted`       | `{ contentId, locale, languageId, version, revisionId? }`                                       | `localization`                 |
| `translation_published`     | `{ contentId, locale, languageId, version, publishedAt, revisionId? }`                          | `localization` + `publication` |
| `translation_unpublished`   | `{ contentId, locale, languageId, version, revisionId? }`                                       | `localization` + `publication` |
| `translation_restored`      | `{ contentId, locale, languageId, version, changedFields, revisionId, restoredFromRevisionId }` | `localization` + `editorial`   |
| `delivery_slug_changed`     | `{ contentId, slug, previousSlug, previousPath, canonicalPath, locale }`                        | `delivery`                     |
| `delivery_redirect_created` | `{ contentId, previousSlug, previousPath, canonicalPath, locale }`                              | `delivery`                     |
| `duplicated`                | `{ actorUserId, contentId, contentTypeId, sourceId }`                                           | `duplication`                  |
| `hidden`                    | `{ actorUserId, contentId, hiddenAt }`                                                          | `visibility`                   |
| `unhidden`                  | `{ actorUserId, contentId }`                                                                    | `visibility`                   |

A few payload details that change what a listener does:

- `contentId` has the type of the content type's [id strategy](/docs/content-engine/id-strategy): a `number` for `serial`, a `string` for `uuid` and `bigint`. A bigint id arrives as its exact decimal string.
- A [duplicate](/docs/content-engine/duplicate-content) emits the copy's `created` with `duplicatedFromId`, one `translation_created` per copied language, then `duplicated`. `duplicatedFromId` is absent on an ordinary create.
- `hidden` and `unhidden` never replace `published` or `unpublished`, because [hiding](/docs/content-engine/content-visibility) does not change the status.
- `changedFields` lists only the fields whose value actually moved, typed as the content type's own field names. On translation events it names localized fields only.
- `restored` replaces `updated` for a rollback, so a listener that cares about field changes should handle both.
- `publishedAt` is when the record first went live, and it is never rewritten. Like every date in these payloads (`scheduledFor`, `hiddenAt`), listeners get a `Date`; code that emits one with `emitContentEvent` passes a `Date` and the engine sends it as an ISO string.
- `emitContentEvent` runs after the write has committed, so a payload that does not match the content type's event schema is not thrown: no listener runs, the problem is logged, and the result's `failures` holds one entry with `module: "validation"`.
- `scheduledBy` and `scheduleId` are set only when a schedule fired the change. `actorUserId` on `scheduled` is the same person as `scheduledBy` later.
- The delivery events arrive alongside `updated`, `restored` or a publication event, never instead of them. `locale` is `null` for a shared slug.

[Container collections](/docs/content-engine/containers) emit their own four events, `content.container.created`, `updated`, `moved` and `deleted`, listed in [Container hierarchy](/docs/content-engine/container-hierarchy#events).

A record waiting for [approval](/docs/content-engine/approvals) emits its `published` or `updated` only when a moderator approves it, once. The submission itself emits `content.approval.submitted`, `approved` and `rejected`, listed in [Built-in events](/docs/dev/events/built-in-events#content-approval-events).

The listener also receives an envelope with the actor, the time and `pluginId`. `pluginId` is always the plugin that owns the content type, even when a core queue task ran the change. Field-by-field descriptions are in [Built-in events](/docs/dev/events/built-in-events#content-engine-events).

## Subscribe to an event

<Steps>
<Step>

### Write the listener

`contentEvent(contentType, action)` from `@vitnode/core/content` returns the event's definition. The payload is typed from the content type, and an action the definition does not enable, such as `contentEvent(categoryContentType, "published")`, does not compile. Nothing needs registering: `buildApiPlugin` registers the definitions of every content type it registers.

```ts title="plugins/newsroom/src/api/lib/listeners.ts"
import { buildEventListener } from "@vitnode/core/api/lib/events";
import { contentEvent } from "@vitnode/core/content";

import { storyContentType } from "@/content/story";

export const announceStoryListener = buildEventListener({
  event: contentEvent(storyContentType, "published"),
  name: "announce-published-story",
  description: "Logs every story that goes live",
  handler: async (c, payload) => {
    await c.get("log").debug(`Story ${payload.contentId} was published`);
  },
});
```

</Step>
<Step>

### Add it to a top-level module

VitNode collects listeners only from the `events` array of a module passed directly to `buildApiPlugin`. A listener on a nested module never runs: `buildApiPlugin` throws in development to say so, and [`vitnode doctor`](/docs/dev/cli/doctor) reports it. Production ignores it.

```ts title="plugins/newsroom/src/api/modules/admin/admin.module.ts (excerpt)"
export const adminModule = buildModule({
  name: "admin",
  routes: [],
  modules: [
    buildContentAdminModule({
      containers: [deskContainers],
      contentTypes: [
        articleContent,
        categoryContent,
        commentContent,
        storyContent,
        explainerContent,
        bulletinContent,
        tagContent,
        eventContent,
        pageContent,
        letterContent,
      ],
    }),
  ],
  events: [announceStoryListener], // [!code ++]
});
```

The blog plugin does the same with its `blogLegacyEventListeners`, which turn `content.blog.post.created` into the older `blog.post.created` event, and the forum listens to `contentEvent(topicContentType, ...)` to expire its cached stats.

</Step>
</Steps>

## Check the result

Save the file, publish a story in **AdminCP → Newsroom → Stories** and look for the debug line in the API terminal. A failing listener does not undo the change. The write has already committed, and the engine logs the failure.

Events from a scheduled publish run in a queue task that retries on failure, so the same `published` event can arrive twice. Make work that must happen once idempotent, for example keyed on `scheduleId`. See [A scheduled event may arrive twice](/docs/dev/events/built-in-events#a-scheduled-event-may-arrive-twice).
