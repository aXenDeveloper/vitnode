`publicWrite` lets signed-in members create records from the site and edit their own, while moderators can edit anyone's. The server sets the owner, checks every field against an allowlist and authorizes every edit; your pages only send forms.

This continues the article from [Content page](/docs/content-engine/public-pages). So far only staff write articles, in the AdminCP. After this page, members write them too, at the same public API.

## Staff content and member content

The AdminCP and public writing are two doors into the same table:

| | AdminCP | Public write |
| --- | --- | --- |
| Who | Staff with the content type's admin permissions | Any signed-in member creates; the owner or a moderator edits |
| Session | AdminCP session | The member's normal session on the site |
| Fields | Every field | Only the fields listed in `publicWrite` |
| Publish, hide, delete | Yes | No. The server decides the status, and there is no public delete |
| Routes | `/api/newsroom/admin/content/article` | `/api/newsroom/content/news` |

<Steps>

<Step>

### Add an owner, versions and the write options

Edit `src/content/article.ts`. Add an `author` field, `editorial` and `publicWrite`:

```ts title="plugins/newsroom/src/content/article.ts"
  fields: {
    title: field.text({ required: true, minLength: 3, maxLength: 200 }),
    slug: field.slug({ source: "title" }),
    body: field.richText({ required: true }),
    author: field.user(), // [!code ++]
  },

  publication: true,

  publicApi: {
    path: "news",
    fields: ["id", "title", "slug", "body", "publishedAt"],
  },

  delivery: true,

  editorial: true, // [!code ++]

  // [!code ++:5]
  publicWrite: {
    ownership: { field: "author" },
    create: { fields: ["title", "body"], status: "published" },
    update: { fields: ["title", "body"] },
  },
```

- **`ownership.field`** names the user field the server fills with the signed-in member on create. It can never be in `create.fields` or `update.fields`.
- **`create`** adds `POST /` and lists what a member may send. `status: "published"` makes a new article live at once; the default, `"draft"`, keeps it private until staff publish it.
- **`update`** adds `GET /{id}/edit` and `PATCH /{id}`, and a `can_edit` moderator permission.
- **`editorial`** adds a `version` number to every article, so an edit form can tell when someone else saved first. It also keeps a [revision history](/docs/content-engine/editorial).

The moderator permission shares the `newsroom:article:can_edit` label you added in [First content type](/docs/content-engine/create-a-content-type#add-the-labels), so there is nothing new to translate.

</Step>

## Check the result

Sign in on the site, copy the value of your `vitnode_auth` cookie from the browser's developer tools, and create an article:

```bash
curl -i -X POST http://localhost:3000/api/newsroom/content/news \
  -b "vitnode_auth=<session>" \
  -H "Content-Type: application/json" \
  -d '{"values":{"title":"Our community garden","body":{"type":"doc","content":[{"type":"paragraph","content":[{"type":"text","text":"We planted tomatoes this week."}]}]}}}'
```

```json title="201"
{
  "approval": null,
  "id": 18,
  "publishedAt": "2026-10-23T19:22:31.230Z",
  "slug": "our-community-garden",
  "status": "published",
  "values": {
    "title": "Our community garden",
    "body": { "type": "doc", "content": [{ "type": "paragraph", "content": [{ "type": "text", "text": "We planted tomatoes this week." }] }] }
  },
  "version": 2
}
```

`values` holds exactly the writable fields, and `version` is `2` because the create and the publish each count. Now try what the server refuses:

| Request | Answer |
| --- | --- |
| The same `POST` without the cookie | `401` with `"code": "CONTENT_UNAUTHENTICATED"` |
| `"title": "Hi"` and `"author": 1` in `values` | `400` with a `too_small` issue on `title` and a `not_writable` issue on `author` |
| The title of an article that exists | `409` with `"code": "CONTENT_UNIQUE_CONFLICT"`, because its slug is taken |

The [Write API](/docs/content-engine/public-write-api) lists every route, body and error. Next, give members a form with [Create form](/docs/content-engine/public-write-frontend).

## Ownership

Every member-written record has exactly one owner, and only the server sets it. On create, the routes take the user from the session and write it into `ownership.field` after validating the payload. The owner never changes through the public routes, not even when a moderator edits the record. If the owner's account is deleted, the field becomes empty and only moderators can edit the record.

## Who may edit

Creating needs a signed-in member. Editing is allowed for:

- **The owner**, while `update.own` is `true` (the default) and the record is not [hidden](/docs/content-engine/content-visibility). Set `update.own: false` to let only moderators edit.
- **Moderators** who hold the content type's `can_edit` moderator permission. Give it in **AdminCP → Staff → Moderators**: add a role or a user, choose **Restricted**, and turn on **Edit articles** under Newsroom. A root role and an **Unrestricted** moderator entry hold every moderator permission.

The admin `can_edit` permission only opens the AdminCP routes, and an AdminCP session never adds powers on the public site. Moderators edit with the same forms as members. [Permissions](/docs/content-engine/public-permissions) shows how a page asks who may edit.

## Security

Each layer below holds even if the one before it has a bug:

- **Separate allowlists.** `publicWrite` fields are independent of `publicApi.fields`. A field can be writable without being public, and public without being writable. Server-managed columns (`id`, `status`, `publishedAt`, `version`, `hiddenAt` and friends), the owner field, file, user, group, repeatable and block fields can never be listed. See [writable fields](/docs/content-engine/public-write-api#writable-fields).
- **Strict schemas.** The request schemas are built from the allowlists alone. An unknown key is a `400`, never silently dropped.
- **Authentication.** An anonymous request gets `401` before its body is read.
- **Ownership** is stamped by the server, as described above.
- **Authorization under a row lock.** An edit reads the record with `SELECT ... FOR UPDATE`, checks the owner or moderator permission, and writes in the same transaction, so the owner that was checked is the owner that is written.
- **Relation targets.** A relation field is writable only when its target content type has a `publicApi`. On every write, each referenced record must be published and visible, otherwise the request is a `400` with the `unavailable` issue code. Missing, draft and hidden targets get the same answer.
- **No existence leaks.** `403` is only for records the public can already read. A draft or a hidden record answers `404`, like a record that does not exist.
- **Rate limit and captcha.** `POST` and `PATCH` requests under `/content/` share a budget of 20 per minute per IP, on top of the write budget every mutation spends. Set `create.captcha: true` to require a [captcha](/docs/dev/captcha) token on every create.
- **Session and CSRF.** The routes use the same session cookie, CORS and CSRF origin checks as every other VitNode API route, and they accept JSON bodies only.

Tune the write budget with `rateLimiter.contentWrite`. Like every rate limit, it is off when `NODE_ENV=development`:

```ts title="apps/api/src/vitnode.api.config.ts"
export const vitNodeApiConfig = buildApiConfig({
  rateLimiter: {
    // [!code ++]
    contentWrite: { points: 10, duration: 60 },
  },
});
```

## Side effects

Public writes trigger the same side effects as AdminCP writes, so nothing new needs wiring:

- [Events](/docs/content-engine/events): `created` on create, then `published` when the record goes live, and `updated` with `changedFields` on an edit that changed something. There are no separate public-write events. A record waiting for [approval](/docs/content-engine/approvals) emits `published` or `updated` when a moderator approves it, plus the `content.approval.*` events.
- The Content Engine syncs [Search](/docs/content-engine/search) after the transaction commits, so an article published on create is searchable straight away.
- On an [editorial](/docs/content-engine/editorial#revisions) content type, each create and edit stores a revision attributed to the signed-in user, and staff can restore it from the AdminCP.

## Containers

A content type organized into [containers](/docs/content-engine/containers), such as discussions in forum boards, lets members pick the container when they create a record. List the `field.container()` in `create.fields`. It cannot be in `update.fields`, so moving a record to another container stays a staff edit. The server resolves the container inside the write's transaction and refuses a missing or foreign one with a `400` on that field.

### Container policies

The server decides whether a new record starts as a draft or goes live. The payload never does. Without container policies, `create.status` decides. When the record's container collection has [publishing policies](/docs/content-engine/container-policies), the container decides instead: who may create, whether new records and edits wait for a moderator, and how long the owner may edit. A new record that waits answers with `status: "draft"` and a pending `approval` object, described in [Approvals](/docs/content-engine/approvals). Without container policies, `create.status: "draft"` stores a plain draft, `status: "draft"` with `approval: null`, and no moderator is asked to review it.
