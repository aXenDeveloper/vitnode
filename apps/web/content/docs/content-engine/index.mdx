The Content Engine turns one TypeScript definition into structured content for your plugin. You describe the fields of a content type, such as an article, and VitNode generates its database table, validation, staff API routes, staff permissions and AdminCP screens. Optional blocks add drafts, a public API, member writing, reports, comments, revisions and more.

## Start here

The beginner tutorial builds one small newsroom, step by step, with an article that has a title, a slug and a body. Each page continues the previous one:

1. [First content type](/docs/content-engine/create-a-content-type): define the article and manage it in the AdminCP.
2. [Drafts & publishing](/docs/content-engine/publication): keep unfinished articles private until staff publish them.
3. [Public API](/docs/content-engine/public-api): let anyone read published articles, and only the fields you choose.
4. [Content list](/docs/content-engine/public-lists): show the articles at `/news`, a page at a time.
5. [Content page](/docs/content-engine/public-pages): give every article its own page at `/news/:slug`.

After that, [Embedded list](/docs/content-engine/public-lists-embed) puts the newest articles under each one, and every guide below builds on the same article.

## What is generated and what you write

The Content Engine owns the data and the rules, and your plugin owns every page readers see:

| You build | The Content Engine provides | Your plugin writes |
| --- | --- | --- |
| The AdminCP screen | The list, search, sorting, create and edit forms, publish and hide actions | The sidebar link and, optionally, [custom cells or form layouts](/docs/content-engine/admincp) |
| A list page | The list route, `defineContentList`, `contentListQueryOptions`, `ContentListResults`, `ContentListPagination` | The route, the row layout and the labels |
| A record page | Slug resolution, `404`s, redirects and metadata through `contentDeliveryPage` | The page component, with `RichTextContent` for rich text |
| A member form | The write routes, ownership, validation, `useContentPublicWrite` | The fields with `AutoForm`, success messages and navigation |
| Edit and Report buttons | `canEdit` and `canReport` per visitor, `useContentPermissions`, `ReportButton` | Where the buttons go |
| Comments | The thread route and its placement rules | The comment section, its composer and its refresh |

The page helpers come from `@vitnode/core/tanstack/content`, and every request goes through the typed [`fetcher`](/docs/dev/fetcher) with `module: "content/<publicApi.path>"`. Public pages are the same for every reader, so they can be cached. The browser asks for anything that depends on the visitor, such as an **Edit** button, and the server checks every write again.

## What each option adds

| From the definition | VitNode generates                                                                      |
| ------------------- | -------------------------------------------------------------------------------------- |
| `fields`            | A Postgres table with system columns and indexes, Zod schemas and a typed service      |
| `admin`             | An AdminCP list with search, sorting and bulk actions, plus create and edit forms      |
| Every content type  | Staff routes and the `can_view`, `can_create`, `can_edit` and `can_delete` permissions |
| `publication`       | Draft and published states, a `can_publish` permission and **Publish** buttons         |
| `publicApi`         | Read-only public routes that return only the fields you list                           |
| `publicWrite`       | Create and edit routes for signed-in members, with server-set ownership                |
| `reports`           | A **Report** button readers use and a moderators' queue                                |
| `thread`            | Nested replies with a route that returns the tree a page at a time                    |
| `delivery`          | Page URLs, SEO metadata, slug redirects and sitemap entries                            |
| `editorial`         | Revisions with restore, preview links and scheduling                                   |
| `liveEditing`       | Field locks, an autosaved shared draft and presence in the AdminCP edit form           |
| `localization`      | A translations table and per-language fields and publishing                            |
| `search`            | Records in the site [search](/docs/content-engine/search) index                        |
| `visibility`        | **Hide** and **Unhide** actions and a `can_hide` permission                            |
| `duplication`       | A **Duplicate** action that copies a record into a new draft                           |

Content types live in code and in your migrations, not in the database. There is no screen for creating a content type at runtime.
