Once a content type has [public pages](/docs/content-engine/public-pages), `delivery.seo` decides which fields fill each page's `<title>`, meta description, Open Graph tags and `robots` tag, and `delivery.sitemap` lists the pages for crawlers. You name fields; the Content Engine reads them from every published record, so editors never fill in a separate SEO form unless you give them one.

The examples use `newsroom.story` from the newsroom plugin and `blog.post` from the blog plugin, which is localized.

## Pick the SEO fields

`newsroom.story` uses its title and excerpt, plus a boolean that hides a record from search engines:

```ts title="plugins/newsroom/src/content/story.ts (excerpt)"
fields: {
  title: field.text({ required: true, minLength: 3, maxLength: 200 }),
  // ...
  excerpt: field.textarea({
    ai: {
      action: "newsroom:story.excerpt",
      mode: "suggestion",
      sourceFields: ["title", "code"],
    },
    maxLength: 500,
    nullable: true,
  }),
  // ...
  noIndex: field.boolean({ nullable: true }),
  // ...
},

publicApi: {
  path: "stories",
  fields: [
    "title",
    "slug",
    "excerpt",
    "featured",
    "category",
    "animation",
    "gallery",
    "noIndex",
    "publishedAt",
  ],
  // ...
},

delivery: {
  redirects: true,
  seo: {
    titleField: "title",
    descriptionField: "excerpt",
    noIndexField: "noIndex",
    openGraph: { titleField: "title", descriptionField: "excerpt" },
  },
  sitemap: { changeFrequency: "weekly", priority: 0.7 },
},
```

| Option                           | Field kinds              | Used for                                                     |
| -------------------------------- | ------------------------ | ------------------------------------------------------------ |
| `titleField`                     | text                     | Page title                                                   |
| `fallbackTitleField`             | text                     | Page title when `titleField` is empty. Needs `titleField`    |
| `descriptionField`               | text, textarea, richText | Meta description                                             |
| `fallbackDescriptionField`       | text, textarea, richText | Description when `descriptionField` is empty                 |
| `noIndexField`                   | boolean, not localized   | `robots` tag and sitemap, see [noindex](#hide-a-record-from-search-engines) |
| `openGraph.titleField`           | text                     | Open Graph title, falls back to the page title               |
| `openGraph.descriptionField`     | text, textarea, richText | Open Graph description, falls back to the page description   |
| `openGraph.imageField`           | file, single, not localized | The cover behind the card, see [Social images](#social-images) |
| `openGraph.generateImage`        | boolean, default `true`  | `false` uses the cover itself as `og:image`, see [Social images](#social-images) |

Every field you name must also be in `publicApi.fields`, because the page shows it to anyone. Leave one out and the definition throws at startup with `... which is not in publicApi.fields`. A field inside a group works (`"seo.title"`). A field inside a repeatable does not, since a page has one title, not a list of them.

Values are trimmed, and an empty one counts as missing, so the fallback kicks in. The blog has no summary field, so it describes every post with its content:

```ts title="plugins/blog/src/content/post.ts"
delivery: {
  seo: {
    titleField: "title",
    descriptionField: "content",
    openGraph: { imageField: "coverImage" },
  },
},
```

`content` is rich text. The Content Engine turns it into plain text, and the page cuts it to 160 characters at a word boundary and adds `…`. No markup ever lands in a meta tag.

The blog plugin's own article editor checks the fields this rule reads in its **SEO** sheet. The sheet belongs to the blog plugin, not to every Content Engine form. It shows how the title and the content's first words will look in search results.

## What reaches the page head

The page's `head` calls `contentDeliveryPageHead` with the resolve route's answer, as shown in [Write the page](/docs/content-engine/public-pages#write-the-page). This is what the HTML gets:

| Tag                                           | Rendered                                                                 |
| --------------------------------------------- | ------------------------------------------------------------------------ |
| `<title>`                                     | Yes, followed by the site title (`- VitNode`)                            |
| `<meta name="description">`                   | Yes, at most 160 characters                                              |
| `<meta name="robots">`                        | Only for a no-index record                                               |
| `<link rel="canonical">`                      | Yes. A localized type adds the `hreflang` links                          |
| `og:title`, `og:description`, `og:type`       | Yes, `og:type` is `article`. From `openGraph` when set, else the page's  |
| `og:url`, `og:site_name`, `og:locale`         | Yes                                                                      |
| `og:image` and its size, type and alt         | Yes, see [Social images](#social-images)                                 |
| `twitter:card`                                | `summary_large_image` with an image, `summary` without                   |

## Social images

With `delivery.seo.openGraph` set, a record page gets an `og:image`, the picture link previews show. The API draws it as a 1200 × 630 card at `/delivery/og/{slug}`, next to the other delivery routes: the Open Graph description as a large quote, signed with the title. `openGraph: {}` is enough to get one.

- **A cover behind the card.** `openGraph.imageField` names a shared, single `field.file()` in `publicApi.fields`; the blog uses its cover. The card shows it on the right side, fading smoothly into the background, and keeps the quote in its own column so no word sits on the picture. Only an image a reader may open counts: a GIF, JPEG, PNG or WebP that no [attachment rule](/docs/content-engine/access-attachments) restricts. The API reads it from your storage, and a new cover gives the card a new URL.
- **The cover on its own.** `generateImage: false` skips the card and uses the `imageField` image itself as `og:image`, with the file's alt text in the page's language. A record without a cover then falls back to the site image.

The resolve route reports the choice under `openGraph.image`:

```json
"openGraph": {
  "title": "Hello Content Engine",
  "description": "A first story from the newsroom plugin, served by the public API and rendered on its own page.",
  "image": {
    "alt": "Hello Content Engine",
    "generated": true,
    "height": 630,
    "type": "image/png",
    "url": "http://localhost:3000/api/newsroom/content/stories/delivery/og/hello-content-engine?v=0k7ophq",
    "width": 1200
  }
}
```

Colours, fonts, templates per content type and caching are covered in [Social images](/docs/dev/social-images).

## Hide a record from search engines

`noIndexField` names one boolean that drives two things together:

- the page gets `<meta content="noindex, nofollow" name="robots"/>`;
- the record leaves the [sitemap](#sitemap).

Only `true` hides a record. `null` and `false` both mean "index it", which is why `newsroom.story` can make the field nullable without emptying its sitemap. The resolve route reports the decision as `"robots": { "follow": true, "index": false }`.

The field must be shared, not localized. A record has one indexing decision, and a per-language value would let the Polish page say `noindex` while the sitemap lists the English one. The definition refuses a localized `noIndexField` for that reason.

## Localized alternates and hreflang

For a [localized](/docs/content-engine/localization) content type, the page head links every published translation of the record. The blog post `english-title` is published in English and Polish, so `/blog/article/english-title` gets:

```html
<link href="http://localhost:3000/blog/article/english-title" rel="canonical"/>
<link href="http://localhost:3000/blog/article/english-title" hrefLang="en" rel="alternate"/>
<link href="http://localhost:3000/pl/wpisy/polish-title" hrefLang="pl" rel="alternate"/>
<link href="http://localhost:3000/blog/article/english-title" hrefLang="x-default" rel="alternate"/>
```

- The canonical link is the page's own language.
- Each URL follows the app's [localized URL rules](/docs/dev/i18n/localized-urls), which is how the Polish post ends up at `/pl/wpisy/...`.
- Links are absolute, built from `VITNODE_WEB_URL` (`http://localhost:3000` when unset) unless a language has its own domain.
- A translation that is not published is not an alternate.
- Delivery on a localized type needs `"id"` in `publicApi.fields`, because alternates are looked up by record id. The definition throws without it.

`hreflang: { xDefault: "defaultLocale" }` adds `hreflang.xDefault` to the resolve route's answer, pointing at the record's default-language URL when that translation is published. It needs `localization`. The page head does not read this option. It adds its `x-default` link whenever the app's default language is among the alternates, with or without it, so the option only matters when you read the resolve route yourself.

```ts title="plugins/blog/src/content/post.ts"
delivery: {
  hreflang: { xDefault: "defaultLocale" },
},
```

## Sitemap

`delivery.sitemap` adds a public route that lists every published URL of the content type, oldest record first. Pass `true` or `{ changeFrequency, priority }`. It needs `publication: true`, since a sitemap lists only what readers can reach.

```bash
curl "http://localhost:3000/api/newsroom/content/stories/delivery/sitemap?cursor=1&limit=1"
```

```json
{
  "entries": [
    {
      "changeFrequency": "weekly",
      "itemId": 3,
      "lastModified": "2026-10-10T11:06:30.518Z",
      "locale": null,
      "path": "/stories/hello-content-engine",
      "priority": 0.7
    }
  ],
  "nextCursor": null
}
```

- A page holds 1,000 entries by default and up to 50,000 with `?limit=`. `cursor` is the `itemId` to continue after, so pass `nextCursor` back as `?cursor=` until it is `null`.
- `lastModified` is the record's `updatedAt`, or the translation's when that is newer.
- Records whose `noIndexField` is `true` are left out, and so are [hidden](/docs/content-engine/content-visibility) records.
- Entries come in id order. For a [uuid](/docs/content-engine/id-strategy) content type that order is lexical, not creation order, and every record still appears once.
- A localized type returns one language per request. Ask for another with `?locale=`:

```bash
curl "http://localhost:3000/api/@vitnode/blog/content/blog/delivery/sitemap?locale=pl&limit=1"
```

```json
{
  "entries": [
    {
      "changeFrequency": "weekly",
      "itemId": 4,
      "lastModified": "2026-08-12T18:00:43.308Z",
      "locale": "pl",
      "path": "/pl/wpisy/polish-title",
      "priority": 0.7
    }
  ],
  "nextCursor": 4
}
```

The app's `/sitemap.xml` does not read these routes for you, so add the entries where you build it. `contentSitemapXml` from `@vitnode/core/content` writes the XML:

```ts
import {
  contentSitemapXml,
  isContentSitemapChangeFrequency,
} from "@vitnode/core/content";
import { fetcher } from "@vitnode/core/tanstack/fetcher";

const response = await fetcher({
  plugin: "newsroom",
  method: "get",
  module: "content/stories",
  path: "/delivery/sitemap",
  args: { query: { limit: 1000 } },
});
if (!response.ok) throw new Error("Could not load the story sitemap.");
const { entries } = await response.json();

const xml = contentSitemapXml({
  origin: "https://example.com",
  entries: entries.map(entry => ({
    ...entry,
    changeFrequency: isContentSitemapChangeFrequency(entry.changeFrequency)
      ? entry.changeFrequency
      : null,
    lastModified: new Date(entry.lastModified),
  })),
});
```

With the newsroom plugin's two published stories, `xml` is:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://example.com/stories/jbbjk-1</loc>
    <lastmod>2026-08-30T09:18:25.398Z</lastmod>
    <changefreq>weekly</changefreq>
    <priority>0.7</priority>
  </url>
  <url>
    <loc>https://example.com/stories/hello-content-engine</loc>
    <lastmod>2026-10-10T11:06:30.518Z</lastmod>
    <changefreq>weekly</changefreq>
    <priority>0.7</priority>
  </url>
</urlset>
```

`contentSitemapIndexXml` writes a `<sitemapindex>` once one file is not enough, for example one file per content type and language.

## Retired slugs

With `delivery.redirects`, an old slug answers a permanent `308` redirect to the record's current URL, so links and search results that still use the old address land on the new page. See [Keep old URLs working](/docs/content-engine/public-pages#optional-next-steps).

## Check the result

Print the SEO tags of a story and of a localized blog post:

```bash
curl -s http://localhost:3000/stories/hello-content-engine | grep -oE '<title>[^<]*</title>|<meta [^>]*name="(description|robots)"[^>]*>|<link [^>]*rel="(canonical|alternate)"[^>]*>'
```

```html
<title>Hello Content Engine - VitNode</title>
<meta content="A first story from the newsroom plugin, served by the public API and rendered on its own page." name="description"/>
<link href="http://localhost:3000/stories/hello-content-engine" rel="canonical"/>
```

The same page also carries the `og:*` tags and `twitter:card` from [What reaches the page head](#what-reaches-the-page-head).

Run the same command for `http://localhost:3000/blog/article/english-title` and you get its title, description and the four links from [Localized alternates](#localized-alternates-and-hreflang). The SVG logo's `<title>Logo VitNode</title>` may show up too; it is not page metadata.

Then ask the resolve route what the page was given, `openGraph` and `robots` included:

```bash
curl http://localhost:3000/api/newsroom/content/stories/delivery/resolve/hello-content-engine
```

Set `noIndex` on a test story, publish it, and run both commands again. The page gains the `robots` tag, and the [sitemap](#sitemap) route stops listing it.
