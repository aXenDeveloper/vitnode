The Content Engine generates the public routes; core ships the helpers that read them, and your plugin owns the pages. Use this table to find the right piece for the interface you are building, then follow its guide.

| You are building | Use | Core provides | Your plugin writes | Guide | Reference |
| --- | --- | --- | --- | --- | --- |
| A list with search, filters and sorting | `defineContentList`, `contentListQueryOptions`, `ContentListResults`, `contentListPageHead` | URL search parsing, the typed query, list states and the head | The route, the controls and each row | [Public lists](/docs/content-engine/public-lists) | [Public lists API](/docs/content-engine/public-lists-api) |
| Pages for that list | `ContentListPagination` | Numbered page links built from the list's URL, which work before hydration | Where it sits | [Public lists](/docs/content-engine/public-lists#render-the-controls-and-the-results) | [Public lists API](/docs/content-engine/public-lists-api) |
| A page per record | `contentDeliveryPage`, `contentDeliveryPageHead`, or `contentPageItem` without delivery | Slug resolution, redirects, `404`s and SEO metadata | The page component | [Public pages](/docs/content-engine/public-pages) | [SEO](/docs/content-engine/seo) |
| A create or edit form | `AutoForm` with `useContentPublicWrite` | Field errors, refusals and version conflicts from the server | The fields, success messages, invalidation and navigation | [Create form](/docs/content-engine/public-write-frontend), [Edit form](/docs/content-engine/public-write-edit) | [useContentPublicWrite](/docs/content-engine/public-write-form-api), [Public write API](/docs/content-engine/public-write-api) |
| Edit and Report buttons that show only when allowed | `useContentPermissions` | `canEdit` and `canReport` for any number of records, per visitor | A small wrapper with the typed `fetcher` call | [Viewer permissions](/docs/content-engine/public-permissions) | [Viewer permissions](/docs/content-engine/public-permissions#usecontentpermissions-reference) |
| A Report button | `ReportButton` with `contentTarget` | The dialog, sign-in prompt and moderators' queue | The type label and an optional preview | [Report content](/docs/content-engine/reports) | [Moderation reference](/docs/dev/moderation/reference#report-ui) |
| Formatted text | `RichTextContent` | Rendering a `field.richText` document as React elements, without an editor or `dangerouslySetInnerHTML` | Typography around it | [Rich text](/docs/content-engine/rich-text#render-it-on-a-public-page) | [Fields](/docs/content-engine/fields) |
| Comments or nested replies | `GET /{path}/thread` through `fetcher`, plus the helpers above | The thread route, tree placement checks and limits | The tree, the composer and the refresh | [Threaded replies on the frontend](/docs/content-engine/threads-frontend) | [`thread` option](/docs/content-engine/reference#thread) |

Imports: the list, page, form and permission helpers come from `@vitnode/core/tanstack/content`; `AutoForm` from `@vitnode/core/components/form/auto-form`; `ReportButton` from `@vitnode/core/tanstack/moderation`; `contentTarget` from `@vitnode/core/content`; `RichTextContent` from `@vitnode/core/components/rich-text`. Every request goes through the typed [`fetcher`](/docs/dev/fetcher) with `module: "content/<publicApi.path>"`.

## Rules that apply everywhere

- **Public data and viewer data are separate.** Lists, pages and threads are the same for every reader and can be cached and server-rendered. `useContentPermissions` asks per visitor in the browser, so shared HTML never contains someone's buttons.
- **The server decides.** Buttons are hints. Every write is authorized again, and a refusal comes back as a message the form shows.
- **Loading follows the app's conventions.** A navigation keeps the current page with the top progress bar, a section that loads on its own gets a skeleton shaped like its content, a refetch keeps the old results visible, and a submit shows its spinner in the button. See [Loading states](/docs/dev/routing/loading).
