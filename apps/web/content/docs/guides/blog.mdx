`@vitnode/blog` is the Content Engine reference plugin. It brings articles,
categories, editorial screens, revisions, a public `/blog` index, article
pages and search indexing, without making your host app impersonate a blog
plugin.

<Steps>
  <Step>

### Install the package

<Tabs groupId="package-manager" persist items={["bun", "pnpm", "npm"]} label="Install @vitnode/blog">

```bash tab="bun"
bun add @vitnode/blog@canary
```

```bash tab="pnpm"
pnpm add @vitnode/blog@canary
```

```bash tab="npm"
npm install @vitnode/blog@canary
```

</Tabs>

  </Step>
  <Step>

### Enable the API plugin

For a Single App, edit `apps/web/src/vitnode.api.config.ts`; a split deployment
uses the same change in `apps/api/src/vitnode.api.config.ts`.

```ts title="apps/web/src/vitnode.api.config.ts"
import { blogApiPlugin } from '@vitnode/blog/config.api' // [!code ++]

export const vitNodeApiConfig = buildApiConfig({
  plugins: [
    blogApiPlugin(), // [!code ++]
  ],
})
```

  </Step>
  <Step>

### Enable the web plugin

One line, and it brings the blog's pages, its AdminCP screens and its
translations with it - your build reads the factory and writes the loaders into
`src/package-messages.gen.ts` for you:

```ts title="apps/web/src/vitnode.config.ts"
import { blogPlugin } from '@vitnode/blog/config' // [!code ++]

export const vitNodeConfig = buildConfig({
  plugins: [
    blogPlugin(), // [!code ++]
  ],
})
```

  </Step>
  <Step>

### Migrate, run, and publish

<Tabs groupId="package-manager" persist items={["bun", "pnpm", "npm"]} label="Prepare and start the blog">

```bash tab="bun"
bun run db:migrate
bun dev
```

```bash tab="pnpm"
pnpm db:migrate
pnpm dev
```

```bash tab="npm"
npm run db:migrate
npm run dev
```

</Tabs>

In AdminCP, create a category at **Blog → Categories**, then publish an article
at **Blog → Articles**. A category's **Friendly URL** is filled in from its name
in each language when you leave it empty, like an article's. The plugin owns the editorial work so the host can stay
boringly reliable.

## Read the blog at /blog

Installing the plugin adds `/blog`: every published article, newest first, 12 to
a page. Drafts, articles scheduled for later and hidden articles never appear.

- The first page opens with the six newest articles as image tiles: one large
  story, two beside it and three below. Each tile shows the article's
  categories, title, authors and date on top of its cover.
- The other articles follow as cards with the cover, up to three categories,
  the title, the excerpt when there is one, the authors with their avatars and
  the date. The whole card opens the article at `/blog/article/:slug`.
- A sidebar lists every category that has articles, with how many each holds.
  Each one opens the category's own page at `/blog/category/:slug`, with its
  articles as cards. On phones the list turns into a row of chips.
- Moving between pages animates with view transitions: an article's cover and
  title grow into the article page, and the category highlight slides to the
  category you picked. Visitors who prefer reduced motion get no animation.

Every view has its own address, so a refresh, a shared link and the back
button all show the same view:

| URL                                | What it shows                                          |
| ---------------------------------- | ------------------------------------------------------ |
| `/blog`                            | Every article, with the image tiles on the first page |
| `/blog?page=2`                     | A later page of every article                          |
| `/blog/category/guides`            | One category's articles, using its friendly URL        |
| `/blog/category/guides?page=2`     | A later page of that category                          |
| `/blog/article/building-a-plugin`  | One article                                            |

Category and article slugs are per language: a Polish reader gets each
category's Polish friendly URL, and a category link in another language
redirects to it. Older links still work: `/blog/:slug` and `/blog?category=3`
redirect permanently to the new addresses. Any other query parameter is
ignored. There is no search box on `/blog`; readers find articles through the
site search, which indexes every published article.

The page follows the reader's language. In Polish it lists the Polish
translation of each article, or the English one where none is published yet,
and category names fall back the same way. "No articles yet" means nothing is
published; "Nothing in this category yet" means the picked category has no
articles in that language, and offers **See all articles**.

The first page of `/blog` and of every category is indexed by search engines,
with a canonical link and `hreflang` alternates that use each language's own
slug. Later pages get `noindex, follow`, so crawlers still reach every
article. Add `/blog` to your app's `/sitemap.xml`
next to the article entries; the
[sitemap route](/docs/content-engine/seo#sitemap) lists articles, not the
index.

### Categories and article counts in your own pages

The sidebar and the category tags come from a small public route that returns
each category's id, name and friendly URL in the requested language, its
friendly URL in every language, its colour and article count, plus the total
for **All articles**:

```bash
curl "http://localhost:3000/api/@vitnode/blog/categories?locale=pl"
```

```json
{
  "items": [
    {
      "articleCount": 4,
      "color": "hsl(215, 81%, 52%)",
      "id": 1,
      "name": "Poradniki",
      "slug": "poradniki",
      "slugs": { "en": "guides", "pl": "poradniki" }
    }
  ],
  "total": 4
}
```

A count only includes articles a reader can open in that language, the same
ones `/blog` lists. Names stay cached until a category changes, and counts until
an article is published, edited, hidden or deleted. To put a blog list on
another page with your own layout, see
[Add a list to another page](/docs/content-engine/public-lists-embed).

### Article authors

The Content Engine never puts user fields in its public API, so the bylines come
from the blog's own route. Pass up to 50 article ids:

```bash
curl "http://localhost:3000/api/@vitnode/blog/authors?posts=4,5"
```

```json
{
  "items": [
    {
      "authors": [
        {
          "avatarColor": "a8295c",
          "avatarUrl": null,
          "id": 1,
          "name": "Ada",
          "nameCode": "ada",
          "role": { "color": null, "prefix": null }
        }
      ],
      "postId": 4
    }
  ]
}
```

Authors come in the order the article lists them. Drafts, scheduled and hidden
articles are left out, so an id never reveals who is writing what.
`blogPostsQueryOptions` calls this route for you and adds `authors` to every
article it returns.

## Write and translate articles

The article editor reads top to bottom like the published article: the cover
image and its alt text, then the title, slug and content. The checks before
publishing live in the **SEO** sheet, so the text gets the whole width.

### Check the article before you publish

Press **SEO** in the header to open the **Ready to publish** sheet. The badge on
the button counts what is still left, so you know when it needs a look. The
sheet checks what a published article usually needs:

| Check                            | Passes when                                                 |
| -------------------------------- | ----------------------------------------------------------- |
| Title fits search results        | Every started language has a title of 60 characters or less |
| Excerpt in every language        | Every started language has an excerpt                       |
| Cover image                      | A cover image is set                                        |
| URL                              | The language you edit has a friendly URL                    |
| Cover alt text in every language | Every started language describes the cover                  |
| Translations complete            | Every language has a title, friendly URL and content        |
| Translations up to date          | No translation is older than the default language           |

The title, excerpt and alt text fields show a live counter against the
recommended length: 60, 160 and 125 characters. They are recommendations, not
limits, so you can still save a longer title.

Each row is green when it is done and says what is missing when it is not, and
the bar on top counts how many are ready. You can fix most rows right there:
write the excerpt in its row, press **Edit under the cover** to jump to the alt
text, or **Open** a language that is missing a translation.

### Publish or unpublish

The header shows whether the article is a **Draft** or **Published** (hover it
to see when it went live). To change that, open the arrow next to **Save
changes** and pick **Publish** or **Unpublish**. It asks for confirmation
first, because readers see the change immediately. **Hide** and **Unhide** live
in the same menu.

### Hide or duplicate an article

The **More actions** menu of an article in the list has **Hide** and
**Duplicate**. Hiding takes a published article off the site, search and the
sitemap without unpublishing it, and **Unhide** brings it back with the same
URL and date. It needs the **Hide and unhide articles** permission. Duplicating
makes a draft copy with every translation, such as "Hello world (Copy)". See
[Hide content](/docs/content-engine/content-visibility) and
[Duplicate content](/docs/content-engine/duplicate-content).

### Translate side by side

Pick a language from **Translate**. Each translated field then shows the default
language on the left, read-only, and the language you translate into on the
right. Your shared fields, such as categories and authors, stay in one place.

A translation is marked **outdated** when the default language was saved after
it. **Generate from title** builds the friendly URL from the translated title.

### Use AI helpers

With AI configured, the editor adds:

- **Translate** on each field, and **Translate missing fields** for a whole
  language. Content keeps its formatting.
- **Write with AI** on the excerpt, which writes it from the title and content.
- **AI review** in the header, which opens a sheet with suggestions about
  clarity, completeness, structure and tone. When a suggestion is about the
  wording, **Show fix** shows the current text next to a rewrite, and **Apply**
  puts the rewrite into the article. **Dismiss** hides a suggestion you do not
  agree with. The review never blocks publishing.

<Callout type="info" title="When the AI buttons appear">
  The buttons appear only when the API has at least one model in `ai.models`.
  The routes behind them require the `can_edit` permission on articles. See
  [AI](/docs/dev/ai) to configure a model.
</Callout>

AI never saves for you. Read the suggestion, then press **Save changes**.
While others are editing the article, a translated body goes into the shared
editor as one change, so everyone sees it and you can undo it.

### Write together

Several people can work on one article at once. The header shows who else is
in it, and a colored outline with a name tag shows who is editing which field. The title,
slug, excerpt and other plain fields are edited by one person at a time; the
article body is shared, with everyone's cursor visible. Your changes are
autosaved to a draft until someone presses **Save changes**. See
[Live editing and autosave](/docs/content-engine/live-editing) for how it
works and what it needs on your server.

### Upgrade an existing blog

Articles have a localized **Excerpt** field. Search results use it as the
description and fall back to the article content when it is empty. The article
content is now stored as [rich text](/docs/content-engine/rich-text) JSON
instead of HTML; the migration keeps the words of existing articles as one
paragraph, so re-check their formatting.

Articles moved from `/blog/:slug` to `/blog/article/:slug`, and categories got
a localized **Friendly URL**. The migration gives every existing category one
made from its name and id, such as `guides-3`; rename it in AdminCP if you want
a shorter one. Old article links redirect, but search results store their URL,
so rebuild the `blog.post` collection in **AdminCP → Debug Panel → Search**
afterwards. If you map the article route in `routePaths`, rename the key to
`'/blog/article/:slug'`.

Run your migrations after you upgrade `@vitnode/blog`:

