A widget is one `defineWidget` call: a bare id, the fields an editor fills in and the React component that renders them. This page covers each part, the fields a widget may hold and how ids are namespaced. For the whole path to a rendered page, follow [First widget](/docs/dev/widgets/end-to-end).

`defineWidget` and `defineBlock` are the same function, exported from `@vitnode/core/widgets` under both names; the types have both names too (`WidgetData` is `BlockData`).

## One call

```tsx title="plugins/newsroom/src/widgets/callout.tsx (excerpt)"
import type { WidgetComponentProps, WidgetData } from '@vitnode/core/widgets'

import { field } from '@vitnode/core/content/fields'
import { defineWidget } from '@vitnode/core/widgets'
import { InfoIcon } from 'lucide-react'

const calloutFields = {
  body: field.textarea({ maxLength: 600, minLength: 1, required: true }),
  title: field.text({ maxLength: 120, minLength: 1, required: true }),
  tone: field.enum({
    defaultValue: 'info',
    values: ['info', 'success', 'warning'],
  }),
}

type CalloutData = WidgetData<typeof calloutFields>

const tones: Record<string, string> = {
  info: 'border-primary/40 bg-primary/5',
  success: 'border-success/40 bg-success/5',
  warning: 'border-destructive/40 bg-destructive/5',
}

const Callout = ({ data }: WidgetComponentProps<CalloutData>) => (
  <aside
    className={`flex flex-col gap-2 rounded-lg border p-4 md:p-6 ${tones[data.tone ?? 'info']}`}
  >
    <h2 className="text-base font-semibold text-balance md:text-lg">
      {data.title}
    </h2>
    <p className="text-sm leading-relaxed text-pretty md:text-base">
      {data.body}
    </p>
  </aside>
)

export const calloutWidget = defineWidget({
  component: Callout,
  description: 'A short highlighted note in one of three tones.',
  fields: calloutFields,
  icon: InfoIcon,
  id: 'callout',
  name: 'Callout',
})
```

`WidgetData<typeof calloutFields>` is the inferred data type: `title` and `body` are `string`, `tone` is `"info" | "success" | "warning" | undefined` because it has a default. Nothing is written twice.

## Register it

A definition does nothing until the plugin exports it. List it in `src/widgets.tsx`, export that object as **`blocks`** (the name VitNode's Vite plugin imports), and pass the same object to `buildApiPlugin({ blocks })` so the API can validate writes:

```tsx title="plugins/newsroom/src/widgets.tsx"
import type { WidgetPluginSource } from '@vitnode/core/widgets'

import { manifest } from '@/manifest.gen'

import { calloutWidget } from './widgets/callout'

export const widgets = {
  pluginId: manifest.id,
  blocks: [calloutWidget],
} satisfies WidgetPluginSource

export const blocks = widgets
```

[First widget](/docs/dev/widgets/end-to-end#give-the-api-the-same-list) shows the `buildApiPlugin` side. A widget missing from either place does not render in the app, or is refused on every write.

## Give it an icon

`icon` is the picture people see next to the widget's name in the [Visual Editor](/docs/dev/widgets/visual-editor): on its card in the catalogue, on the card that follows the pointer while it is dragged, and at the top of its properties panel. Pass the icon **component**, not an element - `icon: InfoIcon`, not `icon: <InfoIcon />` - so the editor can size and colour it to match everything around it.

```tsx
import { MegaphoneIcon } from 'lucide-react'

export const promoWidget = defineWidget({
  component: Promo,
  fields: promoFields,
  icon: MegaphoneIcon,
  id: 'promo',
})
```

Any component that accepts a `className` works, so an icon from another set or your own inline SVG is fine too. Pick one that says what the widget **is** at a glance: a megaphone for a call to action, a "T" for text. Leave `icon` off and the widget gets the generic widget icon, which is fine but makes every such card look alike. Core's own widgets use `PanelTopIcon` (Hero), `MegaphoneIcon` (Call to action) and `TypeIcon` (Text).

The icon only shows up in the editor. Your widget's component on the public page never renders it.

## Component props

```ts
interface WidgetComponentProps<TData> {
  /** The instance's own stable id - not the widget's. */
  blockId: string
  data: TData
  index: number
  type: string
  variant?: string
}
```

`data` is checked against the widget's schema when the page is saved, and its shape is checked again before render, so a component never checks for missing fields. Defaults are filled in when it is saved, not at render. `variant` is the look this instance picked, and is `undefined` for a widget that offers none.

<Callout type="warn" title="A text field is not a safe link">
  The schema checks that a `field.text()` is a string, not that it is a URL you want people clicking. If your widget turns one into an `href`, check it with `isValidNavigationHref` from `@vitnode/core/lib/navigation` first - it allows a site path (`/discover`) or an `https://` URL and refuses `javascript:` and friends. Core's Hero and Call to action widgets simply leave the link out when it fails.
</Callout>

## Two looks, one widget

A widget that should render the same content in more than one shape declares its shapes instead of growing a `style` field:

```tsx
export const featuresWidget = defineWidget({
  component: Features,
  defaultVariant: 'grid',
  fields: featuresFields,
  id: 'features',
  variants: [{ id: 'grid' }, { id: 'list' }, { id: 'compact' }],
})
```

The chosen variant is stored **beside** the instance's data, never inside it, and the editor grows a picker for it with no further work. See [Variants](/docs/dev/widgets/block-variants) for the resolution rules and what happens to a stored variant a widget stops offering.

## Ids are namespaced for you

Write `id: "callout"`. The registry prefixes the namespace of the plugin that registered it, derived from the **last segment** of the package name:

| Plugin               | Widget id      | Stored as              |
| :------------------- | :------------- | :--------------------- |
| `@vitnode/core`      | `hero`         | `core:hero`            |
| `@vitnode/blog`      | `latest-posts` | `blog:latest-posts`    |
| `@acme/page-builder` | `pricing`      | `page-builder:pricing` |

Writing the namespace yourself is an error. A widget would otherwise be addressable under two names, and content written under the wrong one would be unrenderable.

Two packages whose names end in the same segment (`@vitnode/blog` and `@acme/blog`) collide. The registry refuses to build and names both; set `namespace` on one plugin's widgets object (`{ pluginId, namespace: 'acme-blog', blocks: [...] }`) to settle it.

## Which fields a widget may hold

| Kind                                               | Supported | Why                                                                                                                                                 |
| :------------------------------------------------- | :-------- | :-------------------------------------------------------------------------------------------------------------------------------------------------- |
| `field.text()`, `field.textarea()`                 | ✅        | Plain strings, edited in the properties panel.                                                                                                      |
| `field.number()`, `field.boolean()`                | ✅        |                                                                                                                                                     |
| `field.enum()`, `field.dateTime()`                 | ✅        |                                                                                                                                                     |
| `field.group()`                                    | ✅        | Nested objects are ordinary JSON.                                                                                                                   |
| `field.file()`, `field.relation()`, `field.user()` | Not yet   | A reference is a row identifier the owning record has to pin against deletion, and a value inside a JSON document has nowhere to put a foreign key. |
| `field.repeatable()`                               | Not yet   | Its rows are rows on a generated child table, identified by a database id a JSON document does not have.                                            |
| `field.richText()`                                 | Not yet   | Not one of the supported kinds yet.                                                                                                                 |
| `field.slug()`                                     | No        | A slug is a record's address, and a widget is not addressable on its own.                                                                           |
| `field.container()`                                | No        | A container is where a whole record is filed. A widget is part of a record.                                                                         |
| `field.blocks()`                                   | Not yet   | Nested widgets need depth limits, their own allowlist and cycle detection first.                                                                    |

`defineWidget` throws for a refused field, quoting the reason from `blockFieldKindRefusal`. A widget also needs at least one field.

<Callout title="Need an image in a widget?">
  Put the image on the record for now and let the widget choose how to present
  it. A file id inside widget JSON would have no foreign key protecting it from
  deletion, which is why `file`, `relation` and `user` fields wait.
</Callout>

## Localization

A widget's **fields** are never `localized: true`. There is no translation row for them to live in, and per-field locale maps inside JSON would be a second localization system that revisions, preview and the public locale resolution know nothing about.

The **zone** is what translates:

```ts
content: field.blocks({ localized: true })
```

`field.widgets()` is an alias of `field.blocks()`; both build the same field.

This is document-level localization, not translated field values: each language gets its own widgets, in its own order, and the two need not correspond at all.

```text
en:  Hero  →  Text  →  CTA
pl:  Hero  →  CTA   →  Gallery
```

See [Blocks field](/docs/dev/widgets/blocks-field#localization). Text typed in the [visual editor](/docs/dev/widgets/visual-editor#edit-a-widget) goes into the zone of the language the page is showing.

## Validating data by hand

A definition is metadata: an id, the field map and the component. It carries no schema of its own, which is what keeps `defineWidget` - and therefore every public page that renders a widget - free of a validation library. The schema is derived from the fields on demand:

```ts
import { parseWidgetData, widgetDataSchema } from '@vitnode/core/widgets'

const data = parseWidgetData(calloutWidget, { title: 'Heads up', body: '...' })
// { title: "Heads up", body: "...", tone: "info" }

widgetDataSchema(calloutWidget).safeParse(input)
```

`parseWidgetData` applies defaults and throws a `BlockError` naming the field when the value does not fit; its return type is inferred from the definition's field map. `widgetDataSchema` is the underlying Zod object, built once per definition and cached.

A variant is not part of that schema, and neither is the arrangement of the widgets around this one - those are the instance's `variant` and its [Area's layout](/docs/dev/widgets/layout-areas). The rule of thumb: **`data` is what the widget says, `variant` is how this instance says it, `Area.layout` is how widgets sit together.**

The Content Engine calls these for you on every write. You need them only when you are producing widget data outside the API - a seed, a migration, an importer.
