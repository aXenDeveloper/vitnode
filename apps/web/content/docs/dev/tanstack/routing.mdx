---
title: Routing
description: The two ways a URL gets claimed - an app route file, or a plugin's manifest.
---

There are two, and which one you want depends on who owns the page. The app owns
its own routes as files; a plugin declares its routes as data.

<Callout type="info" title="There is a third, and it is not yours">
  VitNode's own screens - `/discover`, `/search`, `/settings`, `/login`, the
  whole AdminCP - are neither. They are **code-based** routes declared in
  `@vitnode/core/tanstack/routes` and mounted onto your tree by
  `withCoreMainRoutes`, `withCoreAdminRoutes` and `withCoreRootRoutes` in
  `src/router.tsx`.

You never write one, and you never edit one: they used to be twenty-nine route
files in every application - all of them wiring around something imported from
the package - and moving them means VitNode can add a screen without an edit in
your app. Your `src/routes` is for **your** pages.

</Callout>

## Mounting VitNode's own routes

The scaffold writes this for you and you will rarely touch it, but it is the one
place your app hands the package what a package cannot know:

```tsx title="apps/web/src/router.tsx"
const loadContentRegistry = async () =>
  (await import("#/lib/content-registry")).contentRegistry;

const routeTree = withCoreRootRoutes(
  withCoreAdminRoutes(
    withCoreMainRoutes(fileRouteTree, { mountUnder: mainShellRoute, pageHead }),
    { loadContentRegistry, mountUnder: adminShellRoute, pageHead },
  ),
  { localeRouting, mountUnder: fileRouteTree, pageHead },
);
```

| Option                | What it answers                                       |
| --------------------- | ----------------------------------------------------- |
| `mountUnder`          | which route frames these screens                       |
| `pageHead`            | your site's name, so every `<title>` ends the same way |
| `localeRouting`       | which locale prefixes exist, for post-sign-in redirects |
| `loadContentRegistry` | which content types your plugins registered            |

<Callout type="warn" title="`loadContentRegistry` is a function, not the registry">
  It is `() => Promise<ContentFrontendRegistry>`, awaited by `/admin/content/*`
  and nothing else. Building a registry reaches the whole Content Engine - `zod`,
  every plugin's admin form components - and `router.tsx` is evaluated on every
  page of your site, so handing over the *value* put all of that in front of your
  front page's first paint.

If you are upgrading from a version that took `contentRegistry`, wrap it: delete
the static import and add the two lines above. See [Initial
bundle](/docs/dev/tanstack/initial-bundle).

</Callout>

## An app-owned route

One file per URL, under `src/routes`. The path comes from the filename.

```tsx title="apps/web/src/routes/_main/about.tsx"
import { createFileRoute } from "@tanstack/react-router";

export const Route = createFileRoute("/_main/about")({
  component: AboutPage,
});

const AboutPage = () => <div className="p-4">About</div>;
```

`_main` is the site shell - the header, the breadcrumb area and the one `<main>`
landmark. It starts with an underscore, so it adds no URL segment: this file is
`/about`, not `/_main/about`. Putting a file under `_admin` instead frames it
with the AdminCP.

## A plugin-owned route

A plugin cannot write a file into the application, so it declares the URL as
data and exports the module that renders it.

```ts title="plugins/my-plugin/src/routes/manifest.ts"
import type { PluginRouteDefinition } from "@vitnode/core/routing";

export const routes: PluginRouteDefinition[] = [
  {
    entry: "routes/hello-page",
    id: "hello",
    path: "/hello",
  },
];
```

```tsx title="plugins/my-plugin/src/routes/hello-page.tsx"
const HelloPage = () => <div className="p-4">Hello</div>;

export default HelloPage;
```

`entry` is a package export subpath, so `routes/hello-page` is imported as
`my-plugin/routes/hello-page`. `id` is a stable name for the page - name it after
the page, not the URL, because it survives a path change.

## Dynamic segments

VitNode has one spelling for a parameter, and it is neither framework's:

```ts
{ entry: "routes/post-page", id: "post", path: "/blog/:slug" }
```

| Where          | How it is written |
| -------------- | ----------------- |
| Plugin manifest | `/blog/:slug`     |
| App route file  | `blog.$slug.tsx`  |

The host converts. Write `:slug` in a manifest and never `$slug`; write `$slug`
in an app route file, because there the filename *is* the path.

## Which shell frames the page

```ts
{ area: "main",  path: "/hello" }          // the public site
{ area: "admin", path: "/admin/my-plugin" } // the AdminCP
```

`area` defaults to `"main"` and chooses a **parent**, never a prefix - an admin
route writes its full `/admin/…` path out. See
[AdminCP routes](/docs/dev/tanstack/admin).

## A route module with behaviour

A page module may export a `route` beside its component:

```tsx title="plugins/my-plugin/src/routes/post-page.tsx"
import type { PluginRoutePageProps } from "@vitnode/core/routing";

import { definePluginRoute } from "@vitnode/core/routing";

interface Post {
  title: string;
}

export const route = definePluginRoute({
  load: async ({ params }) => await fetchPost(params.slug),
  head: ({ loaderData }) => ({ title: loaderData?.title }),
});

const PostPage = ({ loaderData }: PluginRoutePageProps<Post>) => (
  <h1>{loaderData.title}</h1>
);

export default PostPage;
```

`fetchPost` is your own code - a call to your plugin's Hono route through the
[fetcher](/docs/dev/fetcher). VitNode has no data helper of its own here on
purpose: your API is your API.

Four members, all optional:

- **`load`** - everything the page needs before it renders. Runs on the server
  and in the browser, before React.
- **`head`** - the page's `title`, `description` and `robots`, usually read off
  `loaderData`.
- **`breadcrumb`** - a component contributing the label the shell shows. Handed
  no props.
- **`parseSearch`** - normalises the query string into the `search` your `load`,
  `head` and component receive.

<Callout type="warn" title="Write `load` above `head`">
  TypeScript reads an object literal's members in order, so `head`'s `loaderData`
  is only typed once `load` has been read.
</Callout>

<Callout type="info" title="`load` is handed the locale, and nothing else">
  `context` is `{ locale }`. It is not the host's router context and it holds no
  `QueryClient` - a plugin that compiled against one would only install into the
  hosts that happen to have it.
</Callout>
