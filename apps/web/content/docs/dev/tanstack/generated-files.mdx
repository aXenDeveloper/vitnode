---
title: Generated files
description: The five *.gen.ts files in an app, who writes each one, and when.
---

A VitNode app on Vite holds five generated files, all committed, all in `src/`.
Two different tools write them, and knowing which is which is the whole point of
this page.

```txt
src/routeTree.gen.ts               TanStack Router
src/plugin-route-manifest.gen.ts   VitNode
src/plugin-routes.gen.ts           VitNode
src/admin-nav.gen.ts               VitNode
src/content-registry.gen.ts        VitNode
```

Each one says so in its first lines: the header names the tool that will
overwrite your edit.

<Callout type="warn" title="Do not edit them, and do not format them">
  They are rewritten from their inputs on every `vite dev` and `vite build`, so
  an edit survives until the next save. Both tools also emit `/* eslint-disable */`
  and are excluded from Prettier: a formatter that reflows a generated file
  produces a diff on every build, forever.
</Callout>

## The four VitNode writes

One Vite plugin writes all four, in one pass, from one input.

```txt
src/vitnode.config.ts          the plugins this app has
  +  each plugin's exports     routes/manifest, admin/nav, admin/content
  ↓
vitNodePluginRoutes()          @vitnode/core/framework/vite
  ↓
four *.gen.ts                  data, and literal imports
```

| File | Answers | Built from |
| --- | --- | --- |
| `plugin-route-manifest.gen.ts` | _what_ routes exist, at which path, in which shape | each plugin's `routes/manifest` |
| `plugin-routes.gen.ts` | _how_ each route's module is imported | the manifest above |
| `admin-nav.gen.ts` | which plugins contribute AdminCP sidebar entries | which plugins export `admin/nav` |
| `content-registry.gen.ts` | which plugins register content types | which plugins export `admin/content` |

They are four **projections of one list**, which is what matters when you
enable or disable a plugin: removing a line from `src/vitnode.config.ts` removes
that plugin from all four in the same pass, so it cannot be half-installed - no
sidebar entry whose page 404s, no content screen with no route.

Nothing is discovered at runtime and nothing is scanned. A plugin that is
installed but not listed in your config contributes nothing.

### Your plugin's page is not copied anywhere

The registry holds one line per route, and that line is a literal `import()`:

```ts title="src/plugin-routes.gen.ts"
export const pluginRouteModules = {
  "@vitnode/blog:post": () => import("@vitnode/blog/routes/post-page"),
};
```

Because it is literal, the bundler can follow it: your page gets its own chunk
and stays out of the initial download. Because it is an import and not a copy,
your page has exactly one home - the one you wrote it in.

## The one TanStack Router writes

`src/routeTree.gen.ts` is the route tree, generated from the filenames in
`src/routes/`. `tanstackStart()` in `vite.config.ts` writes it. VitNode never
touches it, and neither should anything else.

<Callout type="warn" title="Never install a second route generator">
  `@tanstack/router-cli` ships a `tsr` binary that writes the same file.
  Two generators over one file overwrite each other forever, every write trips
  the dev server's watcher, and the symptom is a page that reloads endlessly for
  no visible reason. `create-vitnode-app` deliberately does not scaffold it.

  The same trap is why a generated app sets `server.strictPort: true` - a second
  `vite dev` has to fail rather than quietly start on port 3001 and fight the
  first one.
</Callout>

## When each one is rewritten

| | `vite build` | `vite dev` start | while `vite dev` runs |
| --- | --- | --- | --- |
| the four VitNode files | yes | yes | on a relevant change |
| `routeTree.gen.ts` | yes | yes | when a route file appears or disappears |

"A relevant change" is narrow on purpose - a rewrite that changed nothing would
trip the watcher and reload your page:

- **`src/vitnode.config.ts`** - you added or removed a plugin.
- **a plugin's `routes/manifest`** - which is also what happens when you rebuild
  a plugin, since `vitnode dev` rewrites its `dist`.
- **a file appearing or disappearing in `src/routes/`** - because adding one of
  your own pages can turn a plugin's legal route into a collision.

Editing a plugin's *page* is not on that list and does not need to be: the app
already imports that module through the registry, so Vite's module graph handles
it - `vitnode dev` writes the file, the server sees a dependency change, the page
reloads. Nothing is regenerated because none of the generated bytes changed.

The same goes for an `admin/nav` or `admin/content` module: the generated file
holds a *specifier*, not your declarations.

<Callout type="info" title="Installing a plugin needs a restart">
  A file that did not exist when the dev server started is not being watched,
  because there was nothing to watch. Adding a package to `package.json` already
  means an install, so restart after one.
</Callout>

## Why they are committed

So that reading the repository tells you the truth about it. These files say
which plugins an install has and which URLs they claim - reviewable information,
which a `.gitignore` entry would hide from every code review.

The cost is that a committed generated file can go **stale**: change a plugin's
manifest, never run the app, and the diff carries a registry describing the
manifest as it was. `apps/web` has a test for exactly that - it regenerates in
memory and compares with what is committed, so a stale file fails CI with the
one instruction that fixes it.

```bash
pnpm dev   # or pnpm build
```

Then commit the result.

<Callout type="info" title="Same inputs, same bytes">
  Every generator here sorts its own input and its own output, so the files do
  not depend on which plugin loaded first, on your machine's locale, or on the
  clock. Two people with the same `vitnode.config.ts` and the same plugin
  versions get byte-identical files - which is what makes "regenerate and diff"
  a meaningful check rather than noise.
</Callout>
