---
title: i18n
description: Render translated text in a page, and declare the namespaces it needs.
---

Text comes from `use-intl`, and a route declares which message namespaces it
renders so they are fetched alongside its code.

## Example

```tsx title="plugins/my-plugin/src/routes/home-page.tsx"
import { useTranslations } from "use-intl";

const HomePage = () => {
  const t = useTranslations("my-plugin.home");

  return <h1>{t("title")}</h1>;
};

export default HomePage;
```

```json title="plugins/my-plugin/src/locales/en.json"
{
  "my-plugin": {
    "home": { "title": "Hello from your plugin" }
  }
}
```

Every key sits under your plugin's own name. A top-level key outside it collides
with core and with every other plugin, and VitNode ignores it.

## Declare the namespaces on the route

```ts title="plugins/my-plugin/src/routes/manifest.ts"
{
  entry: "routes/home-page",
  id: "home",
  path: "/my-plugin",
  namespaces: ["my-plugin.home"], // [!code highlight]
}
```

They live on the route rather than in the module because of a waterfall that is
otherwise unavoidable: a page's strings and a page's code are two requests, and a
list that lived *inside* the code could only be read after downloading the page
it describes. Declared here, the runtime starts both at once.

A child route inherits every namespace its ancestors declare, so a layout can
name the set once for the pages under it.

## When to use it

- **`useTranslations` from `use-intl`**, in every component. Not `next-intl` -
  that pins your plugin to one kind of host.
- **Namespaces are per route, not per plugin.** Name what the page renders; the
  merged tree holds everything else.
- **A missing key falls back to the default locale, per key.** A half-translated
  language shows translated strings where they exist and English where they do
  not, rather than failing.
- **Never put a locale in a route path.** `/my-plugin` serves `/pl/my-plugin`
  too; see [Navigation](/docs/dev/tanstack/navigation).
