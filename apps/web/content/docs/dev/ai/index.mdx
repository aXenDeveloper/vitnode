VitNode integrates the [Vercel AI SDK](https://ai-sdk.dev). Register models in `vitnode.api.config.ts` once, then use them inside any API handler via `c.get("ai")`.

## Quick start

### 1. Configure models in the API config

You can configure models via string identifiers (using AI Gateway) or direct provider instances:

```ts title="apps/api/src/vitnode.api.config.ts"
import { openai } from '@ai-sdk/openai'
import { buildApiConfig } from '@vitnode/core/vitnode.config'

export const vitNodeApiConfig = buildApiConfig({
  // [!code ++:13]
  ai: {
    models: [
      {
        id: 'default',
        name: 'GPT-4o Mini',
        model: openai('gpt-4o-mini'),
        capabilities: ['text', 'structured-output', 'streaming'],
        pricing: {
          rates: { inputPerMillion: '0.15', outputPerMillion: '0.60' },
        },
      },
    ],
  },
})
```

Set `OPENAI_API_KEY` in your `.env` file.

`capabilities` and `pricing` are optional, but [AI actions](/docs/dev/ai/actions) rely on them: capabilities decide which model can run an action, and pricing turns token usage into money. See [Model capabilities](#model-capabilities) and [Costs, Points & Budgets](/docs/dev/ai/costs-and-limits).

---

### 2. Use it in a route handler

For user-facing features, run a registered [AI action](/docs/dev/ai/actions). It checks permissions, limits and budgets, and records the cost:

```ts
handler: async (c) => {
  // [!code ++:4]
  const { output } = await c.get('ai').run({
    action: EXCERPT_AI_ACTION,
    input: c.req.valid('json'),
  })

  return c.json({ text: output })
}
```

For internal tooling you can also resolve the raw model and call the SDK directly - see [AI Usage](/docs/dev/ai/usage).

## Model capabilities

A capability says what a configured language model can do. VitNode never guesses it from the model's name. A model without `capabilities` is treated as `["text"]`.

| Capability          | Meaning                                          |
| :------------------ | :----------------------------------------------- |
| `text`              | Text in, text out.                               |
| `image-input`       | Accepts images in the prompt (vision).           |
| `structured-output` | Returns reliable JSON objects (`Output.object`). |
| `streaming`         | Streams tokens with `streamText`.                |

Every [AI action](/docs/dev/ai/actions) declares the capabilities it needs. When a run starts, VitNode picks the first configured model that has all of them. If no model fits, the run fails with `AI_MODEL_INCOMPATIBLE` before anything is sent to a provider.

<Callout type="warn" title="Vision is not image generation">
  `image-input` means the model can _read_ images, which features such as image
  ALT text need. Generating images is a different thing: register those models
  under `imageModels` and resolve them with `c.get("ai").imageModel()`. Add
  `image-input` only to models whose provider docs say they accept images -
  otherwise VitNode keeps images away from them.
</Callout>

## Model pricing

`pricing` is what the model costs **on this connection**, in USD per one million tokens. Prices are decimal strings, so money never goes through floating point:

```ts title="apps/api/src/vitnode.api.config.ts"
{
  id: 'default',
  name: 'Claude Sonnet',
  model: anthropic('claude-sonnet-4-5'),
  capabilities: ['text', 'image-input', 'structured-output', 'streaming'],
  // [!code ++:8]
  pricing: {
    rates: {
      inputPerMillion: '3',
      outputPerMillion: '15',
      cacheReadPerMillion: '0.30',
      cacheWritePerMillion: '3.75',
    },
  },
}
```

Without pricing, a call's cost stays **unknown** - never zero. Under a budget cap, a model with no pricing is refused with `AI_PRICING_MISSING`. Tiers, flat fees, gateway vs direct pricing and admin overrides are covered in [Costs, Points & Budgets](/docs/dev/ai/costs-and-limits#pricing).

## Multiple models & embeddings

Configure dedicated models for fast completions, reasoning, and vector embeddings:

```ts title="apps/api/src/vitnode.api.config.ts"
ai: {
  models: [
    {
      id: 'default',
      name: 'GPT-4o Mini',
      model: openai('gpt-4o-mini'),
      capabilities: ['text', 'structured-output', 'streaming'],
    },
    {
      id: 'reasoning',
      name: 'Claude Sonnet',
      model: 'anthropic/claude-sonnet-5', // AI Gateway id
      capabilities: ['text', 'image-input', 'structured-output', 'streaming'],
    },
  ],
  embeddingModels: [
    { id: 'default', name: 'Text Embedding 3', model: openai.embedding('text-embedding-3-small') },
  ],
}
```

Resolve specific models by ID:

```ts
const smartModel = c.get('ai').model('reasoning')
const embedModel = c.get('ai').embeddingModel()
const capabilities = c.get('ai').capabilities('reasoning') // ['text', 'image-input', ...]
```

`model()`, `embeddingModel()`, `imageModel()` and `models()` work as before. Admins can assign a different model (and a fallback) to each action in the AdminCP; an assigned model that lacks a required capability is refused.

## Reading the model list in the browser

Provider instances, API keys and prices stay on the server. `c.get("ai").models()` returns only the public half of each entry:

| Field          | Value                                                                 |
| :------------- | :-------------------------------------------------------------------- |
| `id`           | The configured id, e.g. `"default"`.                                  |
| `name`         | The configured label.                                                 |
| `model`        | The provider's model id string, e.g. `"gpt-4o-mini"`.                 |
| `provider`     | `"gateway"` for AI Gateway ids, otherwise the SDK model's `provider`. |
| `capabilities` | The declared capabilities, or `["text"]`.                             |

The middleware route publishes this list, and the browser reads it with
[`useMiddlewareConfigQuery()`](/docs/dev/fetcher#deployment-configuration):

```tsx title="plugins/writer/src/pages/model-picker.tsx"
import { useMiddlewareConfigQuery } from '@vitnode/core/tanstack/auth'

export const ModelPicker = () => {
  // [!code ++:1]
  const { data } = useMiddlewareConfigQuery()

  if (data.ai.models.length === 0) return <p>AI is not configured.</p>

  return (
    <select className="w-full">
      {data.ai.models.map((model) => (
        <option key={model.id} value={model.id}>
          {model.name}
        </option>
      ))}
    </select>
  )
}
```

The first entry is the default - the one `c.get("ai").model()` resolves when a
handler is given no id. The list is empty when no `ai.models` are configured, so
a picker can hide itself rather than offering nothing.
