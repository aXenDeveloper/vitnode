Every content type in VitNode consists of three compact, dedicated files. This strict division keeps your client bundle lightweight while giving server APIs full access to Drizzle ORM.

## The Three-File Architecture

| File Path | Role | Allowed Dependencies |
| :--- | :--- | :--- |
| `src/content/*.ts` | **Client-Safe Definition** | `zod`, `@vitnode/core/content` |
| `src/database/*.ts` | **Database Model** | Drizzle ORM, `@vitnode/core/content/server` |
| `src/config.tsx` | **AdminCP Frontend** | React, Lucide Icons, `@vitnode/core/lib/plugin` |

---

## Step-by-Step Implementation Guide

<Steps>

<Step>
### Step 1: Declare the Content Definition

Create a new file `src/content/article.ts`. Import `defineContentType` and `field` from `@vitnode/core/content`. Do **not** import Drizzle, React, or server utilities here to keep it client-safe.

```ts title="src/content/article.ts"
import { defineContentType, field } from "@vitnode/core/content";

export const articleContentType = defineContentType({
  id: "example.article",
  tableName: "example_articles",
  fields: {
    title: field.text({ required: true, minLength: 3, maxLength: 200 }),
    code: field.text({ required: true, maxLength: 100, unique: true }),
    excerpt: field.textarea({ maxLength: 500, nullable: true }),
    status: field.enum({
      values: ["draft", "published"],
      defaultValue: "draft",
    }),
    publishedAt: field.dateTime({ nullable: true }),
    author: field.user(),
  },
  admin: {
    titleField: "title",
    list: {
      columns: ["title", "code", "status", "author", "updatedAt"],
      searchableFields: ["title", "code", "excerpt"],
      orderableFields: ["title", "code", "status"],
      defaultOrderBy: "updatedAt",
      defaultOrder: "desc",
    },
  },
});
```
</Step>

<Step>
### Step 2: Build the Database Table Model

Create `src/database/articles.ts`. Pass the definition to `createContentModel` to compile the database table representation.

```ts title="src/database/articles.ts"
import { createContentModel } from "@vitnode/core/content/server";
import { articleContentType } from "@/content/article";

export const articleContent = createContentModel(articleContentType);

// Export the table directly so Drizzle Kit discovers it during migrations
export const example_articles = articleContent.table;
```
</Step>

<Step>
### Step 3: Register Content Types in API & Frontend

First, attach the content module to your plugin's admin module on the API side:

```ts title="src/api/modules/admin/admin.module.ts"
import { buildModule } from "@vitnode/core/api/lib/module";
import { buildContentAdminModule } from "@vitnode/core/content/server"; // [!code ++]
import { articleContent } from "@/database/articles"; // [!code ++]
import { CONFIG_PLUGIN } from "@/const";

export const adminModule = buildModule({
  pluginId: CONFIG_PLUGIN.pluginId,
  name: "admin",
  routes: [],
  modules: [
    buildContentAdminModule({ // [!code ++]
      pluginId: CONFIG_PLUGIN.pluginId, // [!code ++]
      contentTypes: [articleContent], // [!code ++]
    }), // [!code ++]
  ],
});
```

Second, register `contentTypeAdmin` in your plugin's frontend configuration:

```tsx title="src/config.tsx"
import { buildPlugin, contentTypeAdmin } from "@vitnode/core/lib/plugin";
import { NotebookPenIcon } from "lucide-react";
import { articleContentType } from "@/content/article"; // [!code ++]

export const examplePlugin = () =>
  buildPlugin({
    pluginId: "@vitnode/example",
    messages,
    contentTypes: [
      contentTypeAdmin({ // [!code ++]
        definition: articleContentType, // [!code ++]
        icon: <NotebookPenIcon />, // [!code ++]
      }), // [!code ++]
    ],
  });
```
</Step>

<Step>
### Step 4: Build Plugins and Run Database Migrations

Generate Drizzle Kit migrations and apply schema updates to your database:

<Tabs groupId='package-manager' persist items={['bun', 'pnpm', 'npm']}>

```bash tab="bun"
bun run build:plugins && bun run db:migrate
```

```bash tab="pnpm"
pnpm build:plugins && pnpm db:migrate
```

```bash tab="npm"
npm run build:plugins && npm run db:migrate
```

</Tabs>
</Step>

</Steps>

## Internationalization (i18n) Configuration

Instead of relying on hardcoded plain text strings in UI components, VitNode humanizes field names automatically and resolves translation keys from your plugin's locale files.

Add i18n translation keys under your plugin namespace in `src/locales/en.json`:

```json title="src/locales/en.json"
{
  "@vitnode/example": {
    "content": {
      "article": {
        "label": "{count, plural, one {Article} other {Articles}}",
        "title": "Articles",
        "desc": "Manage blog articles and news releases.",
        "fields": {
          "title": "Article Title",
          "code": "Article Code",
          "excerpt": "Short Excerpt",
          "publishedAt": "Publication Date"
        },
        "enums": {
          "status": {
            "draft": "Draft Copy",
            "published": "Live"
          }
        },
        "form": {
          "general": { "title": "General information" }
        }
      }
    }
  }
}
```

The translation key convention follows `{pluginId}.content.{entity}` where `entity` corresponds to your content type ID without the plugin prefix (e.g. `example.article` → `article`).

`label` is the record's own noun, written as an [ICU cardinal
plural](https://next-intl.dev/docs/usage/translations#cardinal-pluralization) so a
language with more than two number forms can supply all of them. It is what the
AdminCP interpolates into `Create {name}`, `{name} has been deleted` and every
confirmation, and it is the **only** place that noun is written - a definition
declares no display name. Untranslated, the screens fall back to a name derived from
the id (`example.article` → "Article"). Keys
under `form` title the sections declared in
[`admin.form.sections`](/docs/dev/content-engine/admincp). See [AdminCP
Integration](/docs/dev/content-engine/admincp) for the full key list and its
fallbacks.
