`idStrategy` decides the type of a content type's primary key. The default, `"serial"`, is an auto-incrementing integer. `"uuid"` gives random ids that reveal nothing about how many records exist. `"bigint"` gives integers that never run out. Pick it when you create the content type: changing it later is a [hand-written data migration](#changing-the-strategy-later).

```ts title="plugins/example/src/content/tag.ts"
export const tagContentType = defineContentType({
  id: "example.tag",
  tableName: "example_tags",
  idStrategy: "uuid", // [!code ++]
  localization: { enabled: true, defaultLocale: "en", fallback: "default" },
  fields: {
    name: field.text({ localized: true, required: true, minLength: 1, maxLength: 100 }),
    slug: field.slug({ localized: true, source: "name" }),
    // category and relatedTags relations
  },
  // publication, editorial, publicApi and admin
});
```

## Strategies

| Strategy             | Postgres key                                                               | In JSON and URLs                                             | In TypeScript |
| -------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------ | ------------- |
| `"serial"` (default) | `serial`, up to 2,147,483,647                                              | A number: `42`                                               | `number`      |
| `"uuid"`             | `uuid`, `DEFAULT gen_random_uuid()`                                        | A lowercase string: `"047d2c6c-1d86-47e2-bcd3-2df9f5359541"` | `string`      |
| `"bigint"`           | `bigint GENERATED BY DEFAULT AS IDENTITY`, up to 9,223,372,036,854,775,807 | A decimal string: `"9007199254740994"`                       | `string`      |

Choose by what the ids are for:

- **`serial`** suits most content. Ids are short and readable in URLs and logs. Every existing content type, including the blog, uses it.
- **`uuid`** suits content whose ids should not be guessable or countable, or records created in several places that must not collide.
- **`bigint`** suits tables that may outgrow two billion rows, such as events or logs.

### Why bigint ids are strings

A JavaScript number holds integers exactly only up to 2^53 − 1 (`9007199254740991`). A bigint key can be much larger, and a larger id read as a number is silently rounded to a different record. VitNode never converts a bigint id through `Number`: Drizzle reads the column in `string` mode, and every API, event, cursor and AdminCP URL carries the exact decimal string.

The example plugin's `example.event` uses bigint. Its demo record has an id above 2^53, and the public API returns it intact:

```bash
curl "http://localhost:3000/api/@vitnode/example/content/events/big-launch"
```

```json title="Response (trimmed)"
{
  "id": "9007199254740994",
  "title": "Big launch",
  "slug": "big-launch",
  "primaryTag": { "id": "047d2c6c-1d86-47e2-bcd3-2df9f5359541" },
  "tags": ["047d2c6c-1d86-47e2-bcd3-2df9f5359541"]
}
```

`primaryTag` and `tags` point at `example.tag` records, so they carry UUIDs. Keep bigint ids as strings in your own code too. `Number("9007199254740994")` already gives the wrong record.

## Valid ids

Every route that takes an id parses it with the content type's strategy before touching the database. Anything else answers `400`, never a database error:

| Strategy | Accepted                                                                                 | Refused, for example                   |
| -------- | ---------------------------------------------------------------------------------------- | -------------------------------------- |
| `serial` | A positive integer up to 2,147,483,647, or its digits in a URL                           | `abc`, `0012`, `-1`                    |
| `bigint` | Positive decimal digits up to 9,223,372,036,854,775,807, without a sign or leading zeros | `0012`, `+42`, `9223372036854775808`   |
| `uuid`   | Lowercase, hyphenated 8-4-4-4-12 hex                                                     | An uppercase UUID, `not-a-uuid`, `123` |

Each record has exactly one spelling, so one record is never cached or indexed under two keys.

## Where ids appear

Every Content Engine feature works with all three strategies: the public API, the AdminCP (`/admin/content/example/event/9007199254740994/edit`), delivery and sitemaps, previews, schedules, revisions, events, search, pagination cursors, pickers, [duplicate](/docs/dev/content-engine/duplicate-content) and [hide](/docs/dev/content-engine/content-visibility).

- **Relations** use the key type of the record they point at. A bigint event that links to uuid tags gets a `uuid` foreign key and a `bigint`-to-`uuid` junction table. See [relations across strategies](/docs/dev/content-engine/relations-and-advanced-modeling#relations-across-id-strategies).
- **Shared tables** that reference records of any content type (revisions, schedules, slug history and the search index) store the id as text in a `varchar(64)` `itemId` column. See [Database and migrations](/docs/dev/content-engine/database-and-migrations#ids-and-shared-tables).
- **Events** type `contentId` by strategy: `number` for serial, `string` for uuid and bigint.
- **Sitemaps** page through records in key order. For a uuid content type that order is lexical, not creation order.
- **Repeatable rows** keep their own `serial` ids, whatever the owner uses. User and file references stay integers.

## Helpers

Import these from `@vitnode/core/content` when your own code handles ids:

| Helper                                 | Returns              | Use it to                                                                    |
| -------------------------------------- | -------------------- | ---------------------------------------------------------------------------- |
| `ContentIdOf<typeof eventContentType>` | `number` or `string` | Type an id of one content type                                               |
| `ContentId`                            | `number \| string`   | Type an id in code that handles any content type                             |
| `parseContentIdOf(definition, value)`  | The id, or `null`    | Validate an id from a request, a job payload or a URL                        |
| `contentIdParamSchema(strategy)`       | A Zod schema         | Validate a path or query parameter. A serial id becomes a number             |
| `contentIdSchema(strategy)`            | A Zod schema         | Validate an id inside a JSON body                                            |
| `contentAnyIdSchema`                   | A Zod schema         | Accept an id of any strategy, never rounding a bigint                        |
| `contentIdKey(id)`                     | `string`             | Store an id in a text column, cache key or log. Serial ids keep their digits |
| `contentIdFromKey(strategy, key)`      | The id, or `null`    | Turn a stored key back into an id                                            |
| `compareContentIds(strategy, a, b)`    | `number`             | Sort ids the way Postgres does                                               |

`CONTENT_SERIAL_MAX` (`2147483647`) and `CONTENT_BIGINT_MAX` (`"9223372036854775807"`) are exported too. A custom route that reads an id is shown in [Services, schemas and events](/docs/dev/content-engine/services-and-api#content-ids).

## Changing the strategy later

The strategy is part of the table's schema, and the engine does not convert existing data for you. Do not change `idStrategy` on a content type that has records and run `db:migrate`: the generated SQL cannot turn integer keys into UUIDs.

To switch a live content type, write the data migration yourself:

1. Add the new key column and fill it for every row.
2. Convert every column that references the old key: to-one relation columns in other content types, junction tables (`itemId` and `relatedItemId`), the translations table's `itemId` and repeatable child tables' `itemId`.
3. Rewrite the keys stored in `core_content_revisions`, `core_content_schedules`, `core_content_slug_history` and `core_search_index` for that content type.
4. Swap the primary key and foreign key constraints, then change `idStrategy` and check that a fresh `vitnode migrate --generate` produces no further changes.

Old URLs and API clients that stored the previous ids stop working, so plan redirects if ids appear in public URLs. Creating a new content type and copying the records into it is often simpler.
