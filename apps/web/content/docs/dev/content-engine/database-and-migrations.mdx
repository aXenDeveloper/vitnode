Every content type becomes ordinary Postgres tables managed by Drizzle. `createContentModel` from `@vitnode/core/content/server` builds them from the definition, and the usual migration workflow creates them in your database. Nothing is stored as an untyped JSON document, except `field.blocks()`.

## Generate and apply a migration

After you add or change a content type, run this from the workspace root:

```bash
pnpm build:plugins && pnpm db:migrate
```

1. `build:plugins` compiles your plugin to `dist/`. `db:migrate` does not build, so it would otherwise read the old schema.
2. `db:migrate` runs `drizzle-kit generate`, which compares the exported tables of every configured plugin with the last snapshot and writes a new folder to `apps/api/migrations/`.
3. It applies pending migrations and seeds initial data.

Commit the generated migration with the content type. Production never migrates on startup: run `db:migrate` as a deploy step. More about migrations, including `vitnode migrate --generate` for generation only, is in [Database](/docs/dev/database).

## Export every table

Drizzle Kit discovers tables by reading the exports of `dist/src/database/*.js` in each plugin. A table without an export is left out of the migration without any warning:

```ts title="plugins/example/src/database/recipes.ts"
export const recipeContent = createContentModel(recipeContentType, {
  references: { category: () => example_categories.id },
});

export const example_recipes = recipeContent.table;
export const example_recipes_translations = recipeContent.translationTable;
export const example_recipes_tags = recipeContent.advancedTables.junctions.tags;
export const example_recipes_ingredients =
  recipeContent.advancedTables.repeatables.ingredients;
```

| Model member                       | Exists when                                         |
| ---------------------------------- | --------------------------------------------------- |
| `table`                            | always                                              |
| `translationTable`                 | `localization` is enabled, otherwise `null`         |
| `advancedTables.junctions.<field>` | a `user`, `file` or `relation` field has `multiple: true` |
| `advancedTables.repeatables.<field>` | a `field.repeatable()` exists                     |

## Generated columns

You never declare these; declaring a field with the same name throws.

| Column        | Type                                    | Added when                  |
| ------------- | --------------------------------------- | --------------------------- |
| `id`          | Primary key: `serial`, `uuid` or `bigint`, per [`idStrategy`](/docs/dev/content-engine/id-strategy) | always |
| `createdAt`   | `timestamp`, defaults to `now()`        | always                      |
| `updatedAt`   | `timestamp`, defaults to `now()`, refreshed on every update | always  |
| `status`      | `varchar(32)`, `draft` or `published`, defaults to `draft` | `publication` |
| `publishedAt` | `timestamp`, nullable                   | `publication`               |
| `version`     | `integer`, defaults to `1`              | `editorial`                 |
| `hiddenAt`    | `timestamp`, nullable                   | `visibility`                |
| `hiddenBy`    | `integer`, nullable, references `core_users.id` with `ON DELETE SET NULL` | `visibility` |
| `{field}Text` | `text`, nullable                        | a `field.richText()` listed in `admin.list.searchableFields` or `publicApi.searchableFields` |

Column names are camelCase in SQL, exactly as in TypeScript. Every generated table has row-level security enabled.

The `{field}Text` column holds the plain text of a searchable rich text field, so search matches words instead of HTML tags. It lives on the same table as the field: the main table, the translations table or a repeatable's child table. The engine writes it on every save; you never set it yourself. See [Rich text fields](/docs/dev/content-engine/rich-text#search-and-seo).

### Translations table

With `localization`, `{tableName}_translations` holds the localized fields:

| Column                   | Notes                                                         |
| ------------------------ | ------------------------------------------------------------- |
| `itemId`                 | References the main table, with the same type as its `id`; deleting the record deletes its translations |
| `languageId`             | References `core_languages.id`                                |
| `version`                | Per-language version, always present                          |
| `createdAt`, `updatedAt` |                                                               |
| `status`, `publishedAt`  | With `publication`; each language is published on its own     |

The primary key is `(itemId, languageId)`, so a record has at most one translation per language.

### Junction and child tables

- A **to-many field** gets `{tableName}_{field}` with `itemId`, `relatedItemId`, `position` and `createdAt`, keyed by `(itemId, relatedItemId)`.
- A **repeatable field** gets `{tableName}_{field}` with `id`, `itemId`, `position`, `createdAt`, `updatedAt` and one column per subfield. Deleting the record deletes its rows.
- A **group** adds one camelCase column per leaf to the main table, such as `nutritionCalories`.

Field names are converted to snake_case in table names, so `relatedArticles` becomes `{tableName}_related_articles`.

Every column that points at a record has the type of that record's key. In a junction table, `itemId` follows the owner's `idStrategy` and `relatedItemId` follows the target's. A repeatable's own `id` is always `serial`, while its `itemId` follows the owner. User and file references are always `integer`.

## IDs and shared tables

The [id strategy](/docs/dev/content-engine/id-strategy) sets the key column:

| `idStrategy` | `id` column                                       |
| ------------ | ------------------------------------------------- |
| `"serial"`   | `serial PRIMARY KEY`                              |
| `"uuid"`     | `uuid PRIMARY KEY DEFAULT gen_random_uuid()`      |
| `"bigint"`   | `bigint PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY` |

Four core tables reference records of every content type: `core_content_revisions`, `core_content_schedules`, `core_content_slug_history` and `core_search_index`. Their `itemId` is a `varchar(64)` holding `contentIdKey(id)`: the digits of a serial or bigint id, or the UUID. Migration `20261007095021_content_id_strategies` converted these columns in place from `integer`, so existing serial keys keep their digits:

```sql title="apps/api/migrations/20261007095021_content_id_strategies/migration.sql (excerpt)"
ALTER TABLE "core_content_revisions" ALTER COLUMN "itemId" SET DATA TYPE varchar(64) USING "itemId"::varchar(64);
```

Custom SQL that joins these tables to a content table needs a cast, such as `"core_content_revisions"."itemId" = "example_recipes"."id"::text`.

## Generated indexes

The engine creates these indexes without being asked:

- A unique index on every slug, and on every `field.text({ unique: true })`.
- An index on every single `relation`, `user` and `file` column, and on `hiddenBy` with `visibility`.
- Indexes on `createdAt` and `updatedAt`.
- `(status, publishedAt)` with `publication`.
- On a translations table: `(languageId, status)` or `(languageId)`, plus a unique `(languageId, slug)` for each localized slug.

Add your own with the [`indexes`](/docs/dev/content-engine/reference#indexes) option. An index on the same columns as a generated one replaces it.

## Changing a content type later

Changing a definition is a schema change like any other. Build, migrate and review the generated SQL before you commit it:

- Adding a nullable field, or one with a `defaultValue`, is safe on a table with data.
- Adding a required field without a default fails on a table that already has rows. Add it as nullable first, fill it, then make it required.
- Turning on `localization` moves fields to a new table, and the generated SQL does not copy existing values.
- Switching a `field.textarea()` to `field.richText()` changes no column. Existing values are sanitized the next time each record is saved.
- Making a rich text field searchable adds an empty `{field}Text` column. Until a record is saved again, search falls back to its HTML. To search existing rows by plain text right away, generate the migration with `vitnode migrate --generate` and add an `UPDATE` that fills the column before you apply it. The blog's `20261007084033_content_rich_text_visibility` migration in `apps/api/migrations/` is an example.
- Turning on `visibility` adds two nullable columns, so existing records stay visible.
- Changing `idStrategy` on a table with data is not something the generated SQL can do. It needs a hand-written data migration that converts the key, every column referencing it and the keys in the four shared tables. See [Changing the strategy later](/docs/dev/content-engine/id-strategy#changing-the-strategy-later).
- Never edit or regenerate a migration that has already been applied. Write a new one instead.
