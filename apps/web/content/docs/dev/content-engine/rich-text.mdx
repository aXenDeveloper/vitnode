`field.richText()` stores formatted text, such as an article body, as an HTML string. Editors write it in the AdminCP rich text editor. The API sanitizes the HTML on every write and checks that a required value holds real content, not only an empty `<p></p>`.

Use it instead of `field.textarea()` whenever the value contains formatting. A textarea stores whatever string it receives, and the API does not sanitize it. This guide follows the blog plugin, whose article body moved from a textarea to rich text.

<Steps>

<Step>

### Declare the field

The blog's article `content` is a localized, required rich text field:

```ts title="plugins/blog/src/content/post.ts"
fields: {
  title: field.text({ localized: true, required: true, minLength: 3, maxLength: 255 }),
  content: field.textarea({ localized: true, required: true }), // [!code --]
  content: field.richText({ localized: true, required: true }), // [!code ++]
},
publicApi: {
  enabled: true,
  path: "blog",
  searchableFields: ["title", "content"],
},
```

The field takes the same options as a textarea: `required`, `nullable`, `defaultValue`, `localized`, `minLength`, `maxLength` and `description`. `minLength` and `maxLength` count the characters of the plain text, not the markup, so bold text and links do not use up the limit. All options are in [Fields](/docs/dev/content-engine/fields#rich-text).

</Step>

<Step>

### Build and migrate

Run `pnpm build:plugins && pnpm db:migrate` and restart `pnpm dev`. A rich text field is a Postgres `text` column, the same column a textarea gets, so switching the blog's `content` changed no column.

Because `content` is in `publicApi.searchableFields`, the migration adds a plain-text twin column to the table that holds it, here the translations table. See [Search and SEO](#search-and-seo) below. The blog's migration, `apps/api/migrations/20261007084033_content_rich_text_visibility`, adds it and fills it for existing articles:

```sql title="migration.sql (excerpt)"
ALTER TABLE "blog_posts_translations" ADD COLUMN "contentText" text;
UPDATE "blog_posts_translations" SET "contentText" = ... WHERE "content" IS NOT NULL AND "contentText" IS NULL;
```

The `UPDATE` is hand-written: the generated SQL only adds the empty column. The `UPDATE` approximates the extractor in SQL, and the engine writes the exact text the next time each article is saved.

</Step>

<Step>

### Write in the AdminCP

Open **AdminCP → Blog → Articles** and edit an article. The **Content** field renders the rich text editor, with headings, lists, links, tables and more:

<ImgDocs
  withoutBackground

Any `field.richText()` gets this editor without UI code. It loads lazily, so it does not slow down the rest of the form, and a `localized` field gets a language switcher. The blog replaces the default with its own `BlogArticleEditorField` for a taller writing area. Custom components like that are described in [Customize the AdminCP](/docs/dev/content-engine/admincp#replace-a-field-or-a-cell).

</Step>

<Step>

### Render it on a page

The public API returns the HTML string. The blog's article page renders it with `EditorContent`, which sanitizes it again before inserting it:

```tsx title="plugins/blog/src/pages/post-page.tsx (excerpt)"
import { EditorContent } from "@vitnode/core/components/ui/editor-content";

<div className="text-foreground leading-relaxed text-pretty">
  <EditorContent content={item.content} />
</div>
```

Never render the value with `dangerouslySetInnerHTML` yourself. `EditorContent` applies the same allowlist the API used on write.

</Step>

</Steps>

## What is sanitized and validated

Every write path sanitizes rich text before saving it: create, update, restore, translations, repeatable rows, duplicates and AI translations. The sanitizer keeps the formatting the editor produces and removes everything else:

- **Kept:** paragraphs, headings, lists, task lists, quotes, code, tables, links, images, audio and the editor's inline styles (color, font size, text alignment).
- **Removed:** `<script>`, `<style>`, event handler attributes such as `onclick`, and URLs with a scheme other than `http`, `https` or `mailto`, such as `javascript:` or `data:`.

After sanitizing, the API validates the result:

| Check      | Rule                                                                                                                                    |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `required` | The value must hold text, or an image or audio element with a `src`. `<p></p>`, `<p><br></p>`, `&nbsp;` or a lone `<hr>` count as empty |
| Length     | `minLength` and `maxLength` apply to the plain text. An image-only value fails `minLength`                                              |
| Size       | At most 500,000 characters of HTML (`CONTENT_RICH_TEXT_MAX_HTML_LENGTH`), checked before and after sanitizing                           |

A value that fails is rejected with `400` and an error on that field, which the AdminCP shows under the editor. Input that sanitizes to nothing, such as a lone `<script>`, fails `required`. An optional field that is empty after sanitizing is stored as `null` when it is `nullable`, and as `""` otherwise.

The browser runs only the cheap checks (required and length). Sanitizing happens on the server, so the sanitizer never ships to the browser.

## Search and SEO

Search and SEO read plain text extracted from the HTML. Block elements become separate lines, entities such as `&amp;` are decoded once, and scripts and styles are dropped.

- **Site search:** `search.contentFields` and `search.descriptionField` accept rich text fields and index their plain text.
- **AdminCP and public API search:** a rich text field in `admin.list.searchableFields` or `publicApi.searchableFields` gets a nullable `text` column named after it with a `Text` suffix, such as the blog's `blog_posts_translations."contentText"`, on the same table as the field. Every write keeps it up to date, and `?search=` matches it instead of the raw HTML, so searching for `strong` does not find every bold word. A field name whose twin collides with another column, or is longer than 63 characters, throws when the content type is defined.
- **SEO:** a rich text field can be `delivery.seo.descriptionField` or its fallback. The delivery API returns its plain text, and a value with only an image falls back to the next field.

The same extractor is exported as `htmlToText` and `stripHtml` from `@vitnode/core/lib/strip-html`, if you need plain text in your own code.

A rich text field cannot be a slug `source`, a `titleField` fallback, a filter, a `unique` field or part of a widget. Name it explicitly when you want it searchable: it is never added to the AdminCP search box by default.

## Check the result

Read an article back from the blog's public API:

```bash
curl "http://localhost:3000/api/@vitnode/blog/content/blog/hello-world"
```

```json title="Response (trimmed)"
{
  "id": 701,
  "title": "Hello world",
  "content": "<p>Hello <strong>world</strong> &amp; friends</p><ul><li>one</li><li>two</li></ul>"
}
```

`content` is HTML with the formatting intact. Searching for a word finds the article, while searching for markup does not: `?search=friends` returns it and `?search=strong` returns nothing, because search reads `contentText` ("Hello world & friends one two"). Saving an article with an empty editor, or with only a pasted `<script>`, fails with a required-field error under **Content**.
