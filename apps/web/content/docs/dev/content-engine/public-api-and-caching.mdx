Content Engine allows exposing read-only endpoints to your web frontend while keeping administrative data private.

## Prerequisites & Context

Public read access requires a content type definition (e.g. `articleContentType` in `src/content/article.ts`) compiled into a server model `articleContent` in `src/database/articles.ts`:

```ts title="src/database/articles.ts"
import { createContentModel } from "@vitnode/core/content/server";
import { articleContentType } from "@/content/article";

export const articleContent = createContentModel(articleContentType);
```

- **Field Allowlisting**: By default, no fields are exposed publicly. You must explicitly declare `publicApi.fields`.
- **`buildContentPublicModule`**: An API plugin module from `@vitnode/core/content/server` that mounts public endpoints at `/api/{plugin}/{entity}`.

---

## Step-by-Step Implementation

<Steps>

<Step>
### Step 1: Configure Public API Field Allowlist

In `src/content/article.ts`, add `publicApi` and list fields allowed for public reads:

```ts title="src/content/article.ts"
export const articleContentType = defineContentType({
  id: "example.article",
  tableName: "example_articles",
  publication: true,
  publicApi: { // [!code ++]
    fields: ["title", "code", "excerpt", "publishedAt", "author"], // [!code ++]
  }, // [!code ++]
  fields: {
    title: field.text({ required: true }),
    code: field.text({ required: true }),
    excerpt: field.textarea({ nullable: true }),
    adminNotes: field.textarea({ nullable: true }), // Excluded from public API
  },
});
```
</Step>

<Step>
### Step 2: Register Public API Module

Attach `buildContentPublicModule` at the root level of your API plugin configuration:

```ts title="src/config.api.ts"
import { buildContentPublicModule } from "@vitnode/core/content/server"; // [!code ++]
import { articleContent } from "@/database/articles";

export const exampleApiPlugin = () =>
  buildApiPlugin({
    pluginId: CONFIG_PLUGIN.pluginId,
    modules: [
      adminModule,
      buildContentPublicModule({ // [!code ++]
        pluginId: CONFIG_PLUGIN.pluginId, // [!code ++]
        contentTypes: [articleContent], // [!code ++]
      }), // [!code ++]
    ],
  });
```

This creates:
- `GET /api/example/articles`: Paginated list of published articles.
- `GET /api/example/articles/[id]`: Single published article details.
</Step>

<Step>
### Step 3: Enable Global Search Indexing

Add `search` options to automatically sync items with the global search index:

```ts title="src/content/article.ts"
export const articleContentType = defineContentType({
  id: "example.article",
  tableName: "example_articles",
  search: { // [!code ++]
    titleField: "title", // [!code ++]
    textField: "excerpt", // [!code ++]
  }, // [!code ++]
  fields: {
    title: field.text({ required: true }),
    excerpt: field.textarea({ nullable: true }),
  },
});
```
</Step>

<Step>
### Step 4: Expire the cache tags a write invalidated

Every public read of a content type has a tag, and the tags are **pure string
builders** from `@vitnode/core/content` - no framework, no runtime:

```ts
import {
  contentPublicItemTag,
  contentPublicListTag,
  contentPublicSlugTag,
} from "@vitnode/core/content";

contentPublicListTag("example.article", "en");
contentPublicItemTag("example.article", 42, "en");
contentPublicSlugTag("example.article", "hello-world", "en");
```

They are per locale rather than global on purpose: publishing a Polish
translation changes no English list page, and throwing that cache away would be a
cost with no correctness to show for it.

In the app, a write invalidates the TanStack Query entry it changed:

```ts
await queryClient.invalidateQueries({ queryKey: ["articles"] });
```

<Callout type="warn" title="A background job cannot call your front end">
  A scheduled publish runs in the API process and holds no reference to whatever
  cache is in front of the pages. So it asks over HTTP:
  `dispatchContentRevalidation` posts the invalidated tags to every origin listed
  in `content.revalidateOrigins`, signed with the cron secret. An install whose
  front end caches nothing lists no origin and is never posted at.
</Callout>

See [Cache](/docs/dev/cache) for the whole model.
</Step>

</Steps>
