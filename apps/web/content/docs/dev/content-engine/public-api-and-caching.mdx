Public content is an API concern owned by the plugin. Start with an explicit
allowlist; no field is public just because it looked innocent in a database
column at 2 a.m.

<Steps>
  <Step>

### Define the public response

```ts title="plugins/site-notes/src/content/article.ts"
export const articleContentType = defineContentType({
  id: '@acme/site-notes.article',
  tableName: 'site_notes_articles',
  fields: {
    adminNotes: field.textarea({ nullable: true }),
    excerpt: field.textarea({ nullable: true }),
    slug: field.slug({ source: 'title' }),
    title: field.text({ required: true }),
  },
  // [!code ++:5]
  publicApi: {
    enabled: true,
    fields: ['id', 'title', 'slug', 'excerpt', 'publishedAt'],
    path: 'articles',
  },
})
```

`adminNotes` remains private because it is not in `fields`.

  </Step>
  <Step>

### Build the public module in the plugin API

```ts title="plugins/site-notes/src/config.api.ts"
import { buildApiPlugin } from '@vitnode/core/api/lib/plugin'
import { buildContentPublicModule } from '@vitnode/core/content/server'

import { CONFIG_PLUGIN } from './const'
import { articleContent } from './database/articles'

export const siteNotesApiPlugin = () =>
  buildApiPlugin({
    pluginId: CONFIG_PLUGIN.pluginId,
    modules: [
      // [!code ++:4]
      buildContentPublicModule({
        contentTypes: [articleContent],
        pluginId: CONFIG_PLUGIN.pluginId,
      }),
    ],
  })
```

The module serves published records under the plugin’s public content path, for
example `/api/@acme/site-notes/articles`.

  </Step>
  <Step>

### Only configure revalidation when a front end caches renders

Content mutations already invalidate VitNode’s content tags. If a separate front
end caches its rendered pages, add its origin so the API can notify it through
the framework-neutral revalidation endpoint:

```ts title="apps/api/src/vitnode.api.config.ts"
export const vitNodeApiConfig = buildApiConfig({
  content: {
    // [!code ++]
    revalidateOrigins: ['https://www.example.com'],
  },
})
```

Leave this unset when the front end reads directly from the public content API.
There is no server action to wire up in a plugin.

  </Step>
</Steps>

## Keep the public surface intentional

Use a plugin route for the page that consumes the endpoint, and add search
indexing only when users need to discover the content outside its own section.
