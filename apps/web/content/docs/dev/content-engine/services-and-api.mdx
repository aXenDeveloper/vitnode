The generated routes cover the usual create, read, update and delete. When you need more, such as a "quick dinners" endpoint or a reaction to every published recipe, the model from `createContentModel` gives you typed services, Zod schemas and events.

## Read records in a custom route

`recipeContent.publicService` reads what the public API can read: published records and public fields only. It is typed as optional, because a content type without `publicApi` has none, so check it once.

```ts title="plugins/example/src/api/modules/recipes/quick.route.ts"
import { buildRoute } from "@vitnode/core/api/lib/route";

import { CONFIG_PLUGIN } from "@/const";
import { recipeContent } from "@/database/recipes";

export const quickRecipesRoute = buildRoute({
  pluginId: CONFIG_PLUGIN.pluginId,
  route: {
    method: "get",
    path: "/quick",
    description: "Vegetarian recipes, quickest first",
    responses: { 200: { description: "Quick vegetarian recipes" } },
  },
  handler: async c => {
    const { publicService } = recipeContent;
    if (!publicService) throw new Error("Recipes have no public API.");

    const { edges } = await publicService(c).findMany({
      filters: { vegetarian: true },
      orderBy: { column: "cookingTime", order: "asc" },
      query: { first: "5" },
    });

    return c.json(edges);
  },
});
```

`filters` accepts only `publicApi.filterableFields` and `orderBy.column` only orderable columns. `findBySlug(slug)` and `findById(id)` return one published record or `null`.

## Write records

`recipeContent.service(c)` is the unrestricted service: it sees drafts and every field. Use it in staff routes or background jobs, and check permissions yourself.

```ts
const service = recipeContent.service(c);

const recipe = await service.create({ title: "Pancakes", cookingTime: 20 });
await service.update(recipe.id, { vegetarian: true });
await service.publish(recipe.id);
```

`create` validates its input with the content type's Zod schema and throws a `ZodError` on invalid input. Every method except `findMany` and `options` accepts `{ tx }` as its last argument, so several calls can share a transaction:

```ts
await c.get("db").transaction(async tx => {
  const recipe = await service.create({ title: "Pancakes", cookingTime: 20 }, { tx });
  await service.publish(recipe.id, { tx });
});
```

The plain service does not emit events, store revisions or check versions. The generated routes do all three. When you want the same behaviour from your own code, use the editorial service below or call the generated routes.

| Method                               | Returns                                                                 |
| ------------------------------------ | ----------------------------------------------------------------------- |
| `findMany({ filters, orderBy, query, where })` | `{ edges, pageInfo }`, drafts included                        |
| `findById(id)`                       | The row, or `null`                                                      |
| `findRowById(id)`                    | The row with labels for relations and users, or `null`                  |
| `findDetail(id)`                     | The row with relation, repeatable and file values, or `null`            |
| `create(values)`                     | The new row                                                             |
| `update(id, values)`                 | `{ row, changedFields }`, or `null` when the id does not exist          |
| `delete(id)`                         | The deleted row, or `null`                                              |
| `publish(id)`, `unpublish(id)`       | `{ changed, publishedAt, row }`, or `null`. Only with `publication`     |
| `hide(id)`, `unhide(id)`             | `{ changed, hiddenAt, hiddenBy, row }`, or `null`. Only with `visibility` |
| `duplicate(sourceId, options?)`      | `{ row, sourceId, translations, skippedLocales }`, or `null`. Only with `duplication` |
| `advanced(id)`, `advancedFields(id, fields)` | Values of to-many, repeatable and group fields                  |
| `options(field, search?, ids?)`      | `{ value, label, color? }[]` for a relation or user picker              |
| `relations.<field>`                  | `add`, `remove`, `set`, `reorder`, `get` for a to-many field            |
| `repeatable.<field>`                 | `create`, `update`, `delete`, `reorder`, `set`, `list` for a repeatable |

## Editorial writes

For a content type with [`editorial`](/docs/dev/content-engine/publication-and-editorial), `recipeContent.editorialService` writes the way the AdminCP does: it checks the version, stores a revision and emits events. Like `publicService`, it is optional in the type.

```ts
import { resolveContentActor } from "@vitnode/core/content/server";

const { editorialService } = recipeContent;
if (!editorialService) throw new Error("Recipes have no editorial features.");

const editorial = editorialService(c, { pluginId: CONFIG_PLUGIN.pluginId });

await editorial.update(
  recipeId,
  { title: "Shakshuka for four" },
  { actor: resolveContentActor(c), expectedVersion: 3 },
);
```

When the record's version is no longer `3`, the call throws `ContentVersionConflict` from `@vitnode/core/content`. It carries `itemId`, `expectedVersion` and `currentVersion`, and the generated routes turn it into a `409` with the code `CONTENT_VERSION_CONFLICT`. Background jobs pass `CONTENT_SYSTEM_ACTOR` instead of a request's actor.

## Hide and duplicate

A content type with [`visibility`](/docs/dev/content-engine/content-visibility) or [`duplication`](/docs/dev/content-engine/duplicate-content) adds methods to both services. They exist in the type only when the option is enabled, so calling `hide` on a content type without visibility is a compile error.

| Method                               | Plain service options        | Editorial service options                  |
| ------------------------------------ | ---------------------------- | ------------------------------------------ |
| `hide(id, options)`, `unhide(id, options)` | `{ actorUserId?, tx? }` | `{ actor, expectedVersion?, tx? }`          |
| `duplicate(sourceId, options)`       | `{ overrides?, translations?, tx? }` | `{ actor, overrides?, translations?, tx? }` |

Hiding a record that is already hidden returns `changed: false` and writes nothing. The editorial `hide` and `unhide` raise the version and store a revision. The editorial `duplicate` stores a first revision for the copy and each copied translation.

Like the other service methods, these emit no events. The generated routes run the effects after the transaction commits, and your own code can do the same with the helpers from `@vitnode/core/content/server`:

```ts
import {
  contentVisibilityEffects,
  resolveContentActor,
} from "@vitnode/core/content/server";

const outcome = await editorial.hide(recipeId, {
  actor: resolveContentActor(c),
});

if (outcome) {
  await contentVisibilityEffects(c, recipeContent, outcome, {
    pluginId: CONFIG_PLUGIN.pluginId,
  });
}
```

`contentVisibilityEffects` emits `hidden` or `unhidden`, updates the search index and the delivery data, and notifies [revalidation origins](/docs/dev/content-engine/public-api-and-caching#caching). It does nothing for an outcome with `changed: false`. For a duplicate, call `contentDuplicateEffects`, shown in [Duplicate content](/docs/dev/content-engine/duplicate-content#duplicate-from-your-own-code).

## Content IDs

Service methods take and return ids typed by the content type's [`idStrategy`](/docs/dev/content-engine/id-strategy): `ContentIdOf<typeof recipeContentType>` is `number` for a serial type and `string` for a uuid or bigint type. Never convert an id with `Number()` in code that may meet a bigint type, because ids above 2^53 lose precision.

A custom route reads an id from a URL as text. Parse it with the content type's strategy before calling the service, so a malformed id answers `400` instead of reaching the database:

```ts title="plugins/example/src/api/modules/events/summary.route.ts"
import { parseContentIdOf } from "@vitnode/core/content";
import { buildRoute } from "@vitnode/core/api/lib/route";
import { HTTPException } from "hono/http-exception";

import { CONFIG_PLUGIN } from "@/const";
import { eventContentType } from "@/content/event";
import { eventContent } from "@/database/events";

export const eventSummaryRoute = buildRoute({
  pluginId: CONFIG_PLUGIN.pluginId,
  route: {
    method: "get",
    path: "/{id}/summary",
    description: "Title and status of one event",
    responses: { 200: { description: "The event summary" } },
  },
  handler: async c => {
    const id = parseContentIdOf(eventContentType, c.req.param("id"));
    if (id === null) {
      throw new HTTPException(400, { message: "Invalid event id." });
    }

    const event = await eventContent.service(c).findById(id);
    if (!event) throw new HTTPException(404, { message: "Event not found." });

    return c.json({ id: event.id, status: event.status });
  },
});
```

`id` is a `string` here, because `example.event` uses bigint. With OpenAPI request validation, use `contentIdParamSchema(eventContentType.idStrategy)` for the path parameter instead. It accepts exactly what `parseContentIdOf` accepts and turns a serial id into a number.

Code that handles content types it does not know statically uses `ContentId` (`number | string`) and `contentAnyIdSchema`. To store an id in a text column, a cache key or a log line, use `contentIdKey(id)`; it keeps a serial id's digits unchanged. The generated routes parse their ids with an internal helper that is not exported, so use these helpers in your own code. The full list is in [Record ID strategies](/docs/dev/content-engine/id-strategy#helpers).

## Reuse the schemas

`recipeContent.schemas` holds the Zod schemas the generated routes use. Reuse them so a custom route validates exactly like the built-in ones:

| Schema                | Validates                                             |
| --------------------- | ----------------------------------------------------- |
| `create`              | A create payload, with required fields and defaults   |
| `update`              | A partial update payload                              |
| `select`              | A full row                                            |
| `publicSelect`        | A row as the public API returns it                    |
| `filters`             | Staff list filters                                    |
| `publicFilters`       | Public list filters                                   |
| `form`                | The AdminCP form values                               |

```ts
request: {
  body: {
    content: {
      "application/json": { schema: recipeContent.schemas.create },
    },
  },
},
```

## Events

The generated routes emit an event after every change, named `content.{contentTypeId}.{action}`, such as `content.example.recipe.published`. Register the content type's events once so listeners get typed names and payloads:

```ts title="plugins/example/src/api/lib/events.ts"
import type { ContentEventsFor } from "@vitnode/core/content";

import type { recipeContentType } from "@/content/recipe";

declare module "@vitnode/core/api/models/events" {
  interface VitNodeEvents extends ContentEventsFor<typeof recipeContentType> {}
}
```

Then listen with `buildEventListener`:

```ts title="plugins/example/src/api/lib/listeners.ts"
import { buildEventListener } from "@vitnode/core/api/lib/events";

export const onRecipePublished = buildEventListener({
  event: "content.example.recipe.published",
  name: "announce-new-recipe",
  description: "Logs every newly published recipe",
  handler: async (c, payload) => {
    await c
      .get("log")
      .debug(`Recipe ${payload.contentId} published at ${payload.publishedAt.toISOString()}`);
  },
});
```

Add the listener to the `events` array of a **top-level** module, such as your `admin` module. Listeners on nested modules are not collected.

```ts title="plugins/example/src/api/modules/admin/admin.module.ts"
export const adminModule = buildModule({
  pluginId: CONFIG_PLUGIN.pluginId,
  name: "admin",
  routes: [],
  modules: [buildContentAdminModule({ pluginId: CONFIG_PLUGIN.pluginId, contentTypes: [recipeContent] })],
  events: [onRecipePublished], // [!code ++]
});
```

| Event                       | Payload                                                       | Available with      |
| --------------------------- | ------------------------------------------------------------- | ------------------- |
| `created`, `deleted`        | `{ contentId }`; `created` adds `duplicatedFromId?` with `duplication` | always    |
| `updated`                   | `{ contentId, changedFields }`                                | always              |
| `published`                 | `{ contentId, publishedAt, scheduledBy?, scheduleId? }`       | `publication`       |
| `unpublished`               | `{ contentId, scheduledBy?, scheduleId? }`                    | `publication`       |
| `restored`                  | `{ contentId, changedFields, restoredFromRevisionId, revisionId, version }` | `editorial` |
| `scheduled`                 | `{ contentId, action, actorUserId, scheduledFor, scheduleId }` | `editorial.scheduling` |
| `schedule_cancelled`        | `{ contentId, action, actorUserId, scheduleId }`              | `editorial.scheduling` |
| `translation_created`, `translation_updated`, `translation_deleted`, `translation_published`, `translation_unpublished`, `translation_restored` | `{ contentId, languageId, locale, version, … }` | `localization` |
| `delivery_slug_changed`, `delivery_redirect_created` | `{ contentId, locale, canonicalPath, previousPath, previousSlug, … }` | `delivery` |
| `duplicated`                | `{ actorUserId, contentId, contentTypeId, sourceId }`         | `duplication`       |
| `hidden`                    | `{ actorUserId, contentId, hiddenAt }`                        | `visibility`        |
| `unhidden`                  | `{ actorUserId, contentId }`                                  | `visibility`        |

No event fires when a save changes nothing. Every event, including core's, is listed in [Built-in events](/docs/dev/events/built-in-events).
