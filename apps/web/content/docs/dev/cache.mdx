title: Cache

VitNode has a two-layer caching model, and each layer belongs to exactly one
process:

1. **App cache - TanStack Query.** What the front end keeps, so a page does not
   re-ask for something it already has.
2. **API cache - Redis.** What a Hono route handler keeps, so the database is not
   asked the same expensive question twice.

Caching is **opt-in** on both sides. Dynamic data stays fresh by default.

---

## App caching (TanStack Query)

A route loader warms a cache entry before React runs, and the component reads the
same entry back. That is the whole model - there is no separate render cache and
no directive to remember.

```tsx title="apps/web/src/routes/_main/announcements.tsx"
export const Route = createFileRoute("/_main/announcements")({
  loader: async ({ context }) =>
    await context.queryClient.ensureQueryData(announcementsQuery()),
  component: AnnouncementsRoute,
});
```

```tsx
const { data } = useSuspenseQuery(announcementsQuery());
```

Same options object in both places, so the server-rendered HTML and the first
client render come from one request. See [Data
loading](/docs/dev/tanstack/data-loading).

### The query definition is the contract

Keep the key, the request and the freshness in one exported module:

```ts title="announcements-query.ts"
import { queryOptions } from "@tanstack/react-query";
import { RECORD_STALE_TIME } from "@vitnode/core/lib/query-freshness";

export const announcementsQuery = () =>
  queryOptions({
    queryFn: async () => await fetchAnnouncements(),
    queryKey: ["announcements"],
    staleTime: RECORD_STALE_TIME,
  });
```

### Invalidation

After a write, expire exactly the entry you changed:

```ts
await queryClient.invalidateQueries({ queryKey: ["announcements"] });
```

Not `invalidateQueries()` with no key: the session, the messages and every other
screen's data have not changed because one announcement was published.

<Callout type="warn" title="A key addresses a cache; it never authorizes anything">
  The browser's `QueryClient` is created once per document and outlives a
  sign-out, so a shared key like `["devices", "me"]` would show the next person
  the previous one's data **without a single request being made**. Partition
  private reads by the owner's id, and remember that who may read what is decided
  in Hono, from the session cookie, on every request.
</Callout>

<Callout type="info" title="Plugin routes are the same, minus the client">
  A plugin route's `load` is handed `{ locale }` and no `QueryClient`, so it
  awaits its own fetch and returns the result. Everything above still applies to
  the Hono route it calls.
</Callout>

## API caching (Redis)

Inside your Hono route handlers, use `c.get("cache")` to store expensive query
results in Redis:

```ts title="plugins/stats/src/api/modules/stats.route.ts"
// Cache result on miss for 5 minutes
const stats = await c.get('cache').remember(
  `stats:${containerId}`,
  60 * 5, // TTL in seconds
  async () => await calculateHeavyStats(c, containerId),
);
```

### Invalidation

Delete the key whenever the underlying record changes:

```ts
await c.get('cache').delete(`stats:${containerId}`);
```

<Callout type="info" title="Optional Redis">
  Redis is optional. If not configured, `c.get("cache")` gracefully acts as a
  no-op and runs the callback directly. See [Redis Setup](/docs/dev/advanced/redis).
</Callout>

## Content Engine tags

Content Engine builds its own cache tags for a content type's public reads -
`contentPublicListTag`, `contentPublicItemTag`, `contentDeliveryTag` and friends,
all in `@vitnode/core/content`. They are pure strings: a mutation computes the
tags it invalidated and hands them to whoever keeps the cache.

```ts
import { contentPublicItemTag } from "@vitnode/core/content";

const tag = contentPublicItemTag("blog.post", 42, "en");
```

<Callout type="warn" title="A background job cannot expire a front end's cache by calling a function">
  A scheduled publish runs in the API process, which has no access to whatever
  cache is in front of the pages. So it asks over HTTP:
  `dispatchContentRevalidation` posts the invalidated tags to every origin an
  install opted into through `content.revalidateOrigins`, signed with the cron
  secret. A front end that caches nothing lists no origin and is never posted at.
</Callout>

See [Content Engine caching](/docs/dev/content-engine/public-api-and-caching) for
which tags a content type produces.

## Choosing between them

| The data                                          | Where it belongs                       |
| ------------------------------------------------- | -------------------------------------- |
| The rows one screen renders                       | TanStack Query, keyed by that screen    |
| A private read (sessions, devices, permissions)   | TanStack Query, keyed by the owner's id |
| An expensive aggregate several endpoints share    | `c.get("cache")` in the API             |
| Reference data (role names, resolved permissions) | `c.get("cache")` in the API             |

The rule of thumb: cache in the API when the *answer* is expensive, and in the
app when the *round trip* is.
