The [properties panel](/docs/dev/blocks/visual-editor#the-properties-panel) has one small indignity built into it: to change a heading you look at the sidebar, find the field called _Title_, and type into a box that is nowhere near the heading. It works. It is also the only part of [Visual Edit Mode](/docs/dev/blocks/visual-editor) that still asks somebody to edit a page by looking somewhere else.

**Inline editing** removes that step. A block author wraps the text the block renders, and while the page is being edited a moderator clicks those actual words and types.

```text
Properties panel ─┐
                  ├─► block.data ─► Save
Click the words  ─┘
```

Two ways in, one thing being edited. There is no second content model, no separate draft of the text, and nothing new to save.

## Marking a field editable

One import, one wrapper, no props to thread through:

```tsx title="plugins/example/src/blocks/hero.tsx"
import type { BlockComponentProps, BlockData } from '@vitnode/core/blocks'

import { defineBlock } from '@vitnode/core/blocks'
import { BlockField } from '@vitnode/core/blocks/block-field'
import { field } from '@vitnode/core/content/fields'

const heroFields = {
  description: field.textarea({ maxLength: 400, nullable: true }),
  title: field.text({ maxLength: 120, minLength: 1, required: true }),
}

type HeroData = BlockData<typeof heroFields>

const Hero = ({ data }: BlockComponentProps<HeroData>) => (
  <section className="flex flex-col gap-2">
    <BlockField name="title">
      <h1 className="text-3xl font-semibold text-balance">{data.title}</h1>
    </BlockField>
    <BlockField name="description">
      <p className="text-muted-foreground leading-relaxed text-pretty">
        {data.description}
      </p>
    </BlockField>
  </section>
)

export const heroBlock = defineBlock({
  component: Hero,
  fields: heroFields,
  id: 'hero',
  name: 'Hero',
})
```

That is the entire opt-in. `BlockField` takes the field's `name`, one child element, and an optional `placeholder`.

| Prop          |          |                                                                                         |
| :------------ | :------- | :-------------------------------------------------------------------------------------- |
| `name`        | required | The field in the block's own `fields` map that this text comes from.                    |
| `children`    | required | One element - the heading, the paragraph, whatever you already render.                  |
| `placeholder` | optional | Overrides the built-in `Add {field}` hint shown while the field is empty. Never stored. |

One element, and the editor borrows it. While a page is being edited, the marked element's text is written by the editor rather than by your JSX, so keep the element to the field and nothing else - `<h1>{data.title}</h1>`, not `<h1>{data.title} <Badge /></h1>`. A `ref` you put on that element is yours in view mode and the editor's while editing. Wrap something other than a single element and you get a `<span>` around it plus a development warning saying so.

### Narrowing `name` to this block's fields

`name` is a string, and a typo in a string is a bug you find on a Tuesday. If you would rather find it in your editor, ask for a version of the component that only accepts this block's own field names:

```tsx
import { blockFieldsFor } from "@vitnode/core/blocks/block-field"

const HeroField = blockFieldsFor<typeof heroFields>()

// ✅ name: "title" | "description"
<HeroField name="title">
  <h1>{data.title}</h1>
</HeroField>

// ❌ Type error: "titel" is not a field on this block
<HeroField name="titel">
  <h1>{data.title}</h1>
</HeroField>
```

It is the same component - the factory hands back `BlockField` itself with a narrower prop type, so it costs nothing at runtime and there is no second thing to learn.

## Which fields can be edited this way

Only the two that are plain strings all the way down.

| Kind                                | Inline         | Where it is edited                                                                        |
| :---------------------------------- | :------------- | :---------------------------------------------------------------------------------------- |
| `field.text()`                      | ✅ single line | On the page, or in the properties panel.                                                  |
| `field.textarea()`                  | ✅ multiline   | On the page, or in the properties panel.                                                  |
| `field.number()`, `field.boolean()` | No             | Properties panel. A stepper and a switch are better controls than a caret.                |
| `field.enum()`, `field.dateTime()`  | No             | Properties panel. There is a fixed set of answers, and a date picker knows what they are. |
| `field.group()`                     | No             | Properties panel. A group is a shape, not a sentence - its leaves get their own controls. |

A `<BlockField>` naming something the block does not declare - a typo, a removed field, or an `enum` somebody hoped would work - is **not** a write. In development it logs a warning naming the block and the field; in every mode it renders its children exactly as they are. The worst outcome is a heading that cannot be clicked, never a value written into the wrong place.

<Callout title="The panel is not going anywhere">
  Inline editing is an addition, not a replacement. Every field a block declares
  still has a control in the sidebar, including the two that are also editable
  on the page. Some people would rather fill a form; a `textarea` with six
  paragraphs in it is often easier to work with in a panel than in a page
  layout.
</Callout>

## `text` and `textarea` behave differently, on purpose

They store different things, so they answer the <kbd>Enter</kbd> key differently.

|                   | `field.text()`                             | `field.textarea()`                           |
| :---------------- | :----------------------------------------- | :------------------------------------------- |
| Stores            | A single-line string.                      | A multiline string.                          |
| <kbd>Enter</kbd>  | Finishes the edit. It does not add a line. | Inserts a newline, and the newline survives. |
| <kbd>Esc</kbd>    | Reverts this field.                        | Reverts this field.                          |
| Pasting two lines | Collapses to one line.                     | Keeps both lines.                            |

That is the whole difference, and it is the difference the field already declared. A `text` field that quietly accepted a newline would store a value its own schema rejects, and the first thing to notice would be a failed save.

## No HTML. None.

Paste this into an inline field:

```html
<strong>Hello</strong>
```

and the block stores this:

```text
Hello
```

Not the markup, not a sanitised version of the markup, not `&lt;strong&gt;`. The text, and only the text. The same is true of bold text pasted from a word processor, a link pasted from another page, and anything else a clipboard likes to smuggle: styling is dropped, the words are kept.

This is deliberate and it is worth saying plainly, because the repository would let you believe otherwise. VitNode **does** ship a rich text editor - Tiptap, used by the places that genuinely need formatted content. It is not involved here, and a `text` or `textarea` field is not quietly reinterpreted as rich text because somebody clicked it. What was a string before this feature existed is still a string, in the database and in your component's props.

If a block needs bold words inside a paragraph, that is a real need and this is not the answer to it.

## Two ways in, one state

The heading on the page and the _Title_ box in the sidebar are not two views that are kept in step. They are the same value.

```text
inline edit ──► dispatch({ type: "update", ref, data }) ──► block.data
panel edit  ──► dispatch({ type: "update", ref, data }) ──► block.data
```

Same action, same reducer, same `{ zoneId, areaId, nodeId }` reference to the node being changed. So:

- typing on the page moves the sidebar field, character by character;
- typing in the sidebar moves the text on the page, character by character;
- **Discard** puts both back, because there is one thing to put back;
- an [invalid block](/docs/dev/blocks/visual-editor#content-the-editor-cannot-read) is not editable either way, for the same reason it was not editable before.

There is no sync, because there is nothing to sync.

## Saving is still a button

Nothing is written when you click away. Blur ends the edit and leaves the value in the editor's state, exactly as a keystroke in the properties panel does. The footer says _Unsaved changes_ and waits.

**Save** is what writes, through the [adapter the page passed](/docs/dev/blocks/visual-editor#saving-is-the-hosts-job) - the same adapter, the same payload, the same `changedZoneIds`. Inline editing added no route, no endpoint and no request of its own.

When the save answers with [what it actually stored](/docs/dev/blocks/visual-editor#answer-with-what-you-stored), that snapshot becomes the new baseline and the new text - on the page and in the sidebar together. If your API trims whitespace or clamps a field to its `maxLength`, the heading on the page updates to what was really kept, rather than keeping a version of itself that only ever existed in one browser tab.

## Escape reverts one field, not your afternoon

<kbd>Esc</kbd> while editing puts **that field** back to what it held when the
edit began, and stops there.

|                                      |                                               |
| :----------------------------------- | :-------------------------------------------- |
| The field you are typing in          | Back to what it was when you clicked into it. |
| The other field on the same block    | Untouched.                                    |
| The block you moved five minutes ago | Untouched.                                    |
| The whole page                       | Still dirty, still unsaved, still yours.      |

The page-wide undo is called **Discard**, it lives in the sidebar footer, and it asks first. <kbd>Esc</kbd> is the small one on purpose: an escape key that threw away an afternoon's arranging would be the most expensive key on the keyboard.

## Empty fields show a hint, not a value

A field with nothing in it would otherwise be an invisible target - a zero-height paragraph nobody can click. So while a field is empty and the page is being edited, it draws a placeholder: the block's own `placeholder`, or _Add description_ built from the field's name.

It is drawn, never stored. Leave it alone and the field stays empty: **Save** sends an empty string, the public page renders what it always rendered for an empty field, and nobody ever sees the word _Add_ anywhere.

Unless the field said otherwise, of course. A `field.text({ required: true, minLength: 1 })` is not satisfied by nothing, and emptying it is not a way around that: the editor says the text does not fit the field yet and **Save** stays blocked until it does - the same answer the properties panel has always given, in the place you are typing.

## Preview turns it off completely

**Preview** already gives a block's links and buttons back by dropping the `inert` wrapper. It does the same to inline editing: no caret, no placeholder, nothing focusable that a visitor would not have.

That matters more here than it looks. The point of Preview is to answer _what does this actually look like?_, and a placeholder reading _Add description_ where a visitor sees nothing is exactly the kind of thing that makes the answer a lie. **Back to editing** brings the carets and the hints back, with every unsaved word intact.

## Dragging still starts at the handle

Text you can click into and blocks you can drag around are, on the face of it, a conflict: press on a heading and drag, and the editor has to decide whether you meant to move the block or select some words.

It does not have to decide, because the answer never changed. **Drag and drop starts at the drag handle**, as it always has. Pressing on the words places a caret and selects text; it never picks the block up. The handle, the keyboard drag, the insertion line and every announcement described in [Drag and drop](/docs/dev/blocks/visual-editor#drag-and-drop) work exactly as before.

Clicking a block still selects it and opens its **Properties**, too. Clicking an inline field selects the block _and_ puts the caret where you clicked, which is what you wanted both times.

## Blocks inside an Area are no different

A block sitting inside an [Area](/docs/dev/blocks/layout-areas) is edited the same way, through the same reference:

```ts
interface EditorNodeRef {
  areaId: null | string
  kind: 'area' | 'block'
  nodeId: string
  zoneId: string
}
```

`areaId` is `null` for a block at the root of a zone and the Area's id for a child of one. Everything else - the field name, the action, the reducer - is identical. Two copies of the same block, one at the root of `after-profile` and one inside an Area in it, are told apart by that ref, so typing into one never edits the other.

## Which language am I typing in?

The one the page is showing. And that is the whole design, not a simplification of it.

A block's own fields are **never** `localized: true`. The Content Engine refuses it, by name, with a suggestion:

```text
Field "title" is `localized: true`. A block's fields are not columns, so there is
no translation row for them to live in - localize the whole zone with
`field.blocks({ localized: true })`, which gives each language its own blocks and
its own order.
```

Localisation belongs to whoever owns the zone, one level up. A [`blocks()` field marked `localized: true`](/docs/dev/blocks/blocks-field#localization) gives every language its own list of blocks, its own order, and its own copy of each block's `data`. English and Polish are two documents, not one document with translated strings in it.

So inline editing needed no localisation design of its own:

|                                   |                                                                                                 |
| :-------------------------------- | :---------------------------------------------------------------------------------------------- |
| What you are editing              | The `block.data` in the snapshot the page mounted for the locale it is rendering.               |
| Where it is saved                 | The zone it came from, through the adapter that already knew how to write that locale's row.    |
| What `data` looks like afterwards | `{ title: "Hello" }`. Not `{ title: { en: "Hello" } }`. There is no per-field locale map, ever. |

### Switching locale while the editor is open

Switching language re-renders the page with a different `blocks` array, and a mounted zone [already has a rule](/docs/dev/blocks/visual-editor#content-that-changes-underneath-the-editor) for content arriving underneath it:

|                   |                                                                                                                                                                                  |
| :---------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Zone is clean** | It adopts the incoming snapshot, working copy and baseline together, and stays clean. The new locale's text is what you see and what you edit.                                   |
| **Zone is dirty** | Local edits win. Nothing about its content moves until **Save** or **Discard** resolves them, and the editor remembers the snapshot it skipped so it can settle without a merge. |

Nothing about that is new for inline editing, and nothing about it was changed for inline editing. The text on screen belongs to the snapshot that is mounted - there is no stale sentence left over from the locale you came from, because there was never a second place for one to live.

<Callout title="One language at a time" type="warn">
  There is no "translate this block" action, no side-by-side pair of languages,
  and no link saying *this paragraph is the translation of that paragraph*.
  Adding a block to one language does not add it to the others. That is the cost
  of document-level localisation, and [The `blocks()`
  field](/docs/dev/blocks/blocks-field#localization) is where the trade is
  argued.
</Callout>

## A visitor loads none of this

The [lazy-loading guarantee](/docs/dev/blocks/visual-editor#the-lazy-loading-guarantee) still holds, and `BlockField` was built to keep it.

On a page nobody is editing, `BlockField` asks one question - _is an inline runtime present?_ - and the answer is `null`. It returns its children and stops:

```text
view mode   <BlockField><h1>Hello</h1></BlockField>   →   <h1>Hello</h1>
```

Not a wrapper `<span>`. Not a `data-` attribute. Not a `contenteditable` set to `false`. The markup a visitor receives is byte-for-byte the markup the block rendered before anybody added inline editing, which also means adding it to an existing block changes nothing about your page's HTML, CSS or layout.

`@vitnode/core/blocks/block-field` reaches React and one tiny context module, and nothing else. The editor code that makes a heading typeable is loaded on the first click of **Edit page**, with the rest of the editor, or never.

## The whole thing, once

**What the block author writes:**

```tsx
const HeroField = blockFieldsFor<typeof heroFields>()

const Hero = ({ data }: BlockComponentProps<HeroData>) => (
  <section className="flex flex-col gap-2">
    <HeroField name="title">
      <h1 className="text-3xl font-semibold text-balance">{data.title}</h1>
    </HeroField>
    <HeroField name="description">
      <p className="text-muted-foreground leading-relaxed text-pretty">
        {data.description}
      </p>
    </HeroField>
  </section>
)
```

**What the moderator does:**

<Steps>
<Step>

**Clicks Edit page**

The page grows its zone outlines and its sidebar. The hero looks exactly as it did.

</Step>
<Step>

**Clicks the hero's headline and types**

A caret lands in the real `<h1>`. The words change under the cursor, in the page's own font, at the page's own size, wrapping the way they will wrap for a visitor.

</Step>
<Step>

**Glances at the sidebar**

The hero is selected and **Properties** is open. Its _Title_ field holds the same words, updated as they were typed.

</Step>
<Step>

**Presses <kbd>Enter</kbd>**

`title` is a `field.text()`, so the edit finishes. The heading stays one line, which is the only shape a single-line string has.

</Step>
<Step>

**Clicks the description and pastes a formatted sentence**

The bold survives the journey from the word processor to the clipboard and dies on arrival. The sentence lands as text.

</Step>
<Step>

**Changes their mind and presses <kbd>Esc</kbd>**

The description goes back to what it was when they clicked into it. The headline they typed two steps ago is still the new one, because <kbd>Esc</kbd> reverts the field being edited and nothing else.

</Step>
<Step>

**Presses Preview**

Carets and placeholders go. The hero is a hero. **Back to editing** returns everything, unsaved.

</Step>
<Step>

**Presses Save**

One request, through the page's adapter, carrying the zones that changed. The toast says _Page saved_, the footer says _Saved_, and the text on the page is whatever the server said it stored.

</Step>
</Steps>

## Verifying it yourself

`/example/zones` is the manual test page, and both of its example blocks opt in: `example:callout` marks its title and body, `example:features` marks its heading and intro. The page's own **What to look for once you click Edit widgets** checklist carries the inline-editing rows - clicking a rendered heading, the sidebar agreeing, <kbd>Esc</kbd> reverting one field, Preview switching it off - and its view-mode checklist has the one that matters most:

> No wrapper element around the heading, no `contenteditable` anywhere in the DOM, exactly the markup those blocks rendered before inline editing existed.

Open DevTools on the public page and search the DOM for `contenteditable`. Nothing. That is the feature working.
