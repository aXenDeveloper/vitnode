Every recipient gets their own inbox items, and every member has one stored unread count. Each change to an inbox updates that count in the same database transaction and then pushes the new value to the member's open tabs. This page explains how read state, grouping and the live count behave, so you can predict what members see.

## Read and unread

An inbox item is unread while it is not archived and the member has not read its latest activity. Each item has two counters:

- `activitySeq` starts at 1 and increases each time a grouped notification joins the item.
- `readSeq` records how far the member has read.

Opening the bell or switching its tabs never marks anything read. Opening an item, marking it read or **Mark all as read** does.

When the browser marks an item read, it sends the `activitySeq` it displayed as `throughSeq`. If a fourth reply joined the item after the bell rendered it, the item stays unread, because the member has not seen that reply yet.

**Mark all as read** marks everything that exists when the request takes the member's lock. A notification delivered a moment later stays unread, so nothing that arrives during the click is lost.

## Grouping

Types with [`grouping`](/docs/dev/notifications/notification-types#grouping) merge related notifications into one item per member, type, group key and time window:

- Windows are fixed UTC slots, not sliding ones. With a 60-minute window, 14:00 to 14:59 UTC share an item, and 15:00 starts a new one.
- A new notification in a read item makes it unread again, and one in an archived item brings it back to the inbox.
- Items sort by their latest activity, so a grouped item moves to the top when it grows.
- The unread count counts items, not notifications. Ten replies in one grouped item add 1.

## Items that are no longer available

Before returning a page of the inbox, core checks every item again: the type is still registered, its stored data still parses, `access` still allows the member and `present` still renders. If the type is gone, the data no longer parses or `access` says no, the item is deleted for good and the unread count drops with it. That covers deleted or hidden content, revoked access and uninstalled plugins. Showing the content again does not bring the item back.

If `access` throws or `present` fails, the item is left out of that page but kept, since the cause may be a passing error or a bug about to be fixed. The error is logged.

## The live unread count

The browser receives the same `{ unread, revision }` pair from three places:

1. The session payload, `user.notifications` in `GET /api/@vitnode/core/users/session`, read fresh on every request.
2. The WebSocket message `notificationsStateChannel`, sent after every committed inbox change and once each time a signed-in socket opens.
3. `GET /api/@vitnode/core/notifications/state`, only used when there is no socket.

`unread` is always the absolute count. `revision` increases with every change, and the browser keeps the state with the highest revision, so a slow response never undoes a newer realtime update. Messages are sent only after commit, so a rolled-back change never reaches the browser.

WebSocket messages missed while a tab was offline are not replayed. Instead, the server sends the current count as the first message on every new connection, so a reconnect catches up without an extra request. While the socket is open, the browser never calls `/state`. Without a socket, for example in a single app without `webSocket: true` or while the connection is down, it reads `/state` every 60 seconds while the tab is visible, and right away when a tab returns after more than 30 seconds in the background.

When the count changes, open notification lists refresh once per burst: 1 second after the last change and at most 5 seconds after the first.

## Toasts for new notifications

When a new notification lands in a member's inbox while a tab is open, it also pops up as a toast: the sender's avatar with a small badge for the kind of notification (@ for a mention, an arrow for a reply, a smile for a reaction), their name, what happened and the text. The whole toast is one button. Clicking it opens the notification and marks it read, just like clicking it in the bell. The server adds the member's own `notificationId` to the `created` message, and the browser fetches that item and shows it if it is still unread.

The same badge marks each item in the bell. Admin messages skip it, because the AdminCP already sends them as a live toast of their own.

Every open tab shows the toast. Without a socket there are no toasts; the count still catches up through `/state`.

<Callout type="warn" title="Several API instances need Redis for realtime">
  With `REDIS_URL` set, realtime messages travel between API instances over
  Redis, so delivery on instance A reaches a tab connected to instance B.
  Without Redis, only tabs connected to the same instance update live. Others
  catch up on their next reconnect or page load. See
  [Redis](/docs/dev/advanced/redis).
</Callout>

## What core ships in the UI

| Piece                  | Where                                                                                                                         |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Bell with unread badge | Site header on every screen size. Loads nothing until opened                                                                  |
| Bell dropdown          | **Unread** (default), **All** and **Mentions** tabs. Scrolls through the whole inbox, 20 items at a time, as a virtual list |
| Row actions            | Mark read or unread and archive, on hover or focus, always visible on touch screens                                          |
| Preferences            | `/settings/notifications`, see [Preferences](/docs/dev/notifications/preferences)                                             |

The dropdown is the only inbox screen; there is no separate notifications page.

A default theme needs no wiring. To build your own bell, call the [member endpoints](/docs/dev/notifications/reference#member-endpoints) and listen to the [realtime channel](/docs/dev/notifications/reference#realtime-channel).
