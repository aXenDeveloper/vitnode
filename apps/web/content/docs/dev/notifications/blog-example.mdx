The `@vitnode/blog` plugin uses the Notifications Center for one feature: readers
follow a blog category, and get "New article: …" when an article in it is
published. All of it lives in `plugins/blog/src/api/lib/notifications.ts`, and
it touches every part of the API.

<Steps>

<Step>

### Declare the type

```ts title="plugins/blog/src/api/lib/notifications.ts"
export const postPublishedNotification = buildNotificationType({
  id: 'blog.post_published',
  version: 1,
  schema: z.object({
    postId: z.number().int().positive(),
    slug: z.string().min(1).max(255),
    title: z.string().min(1).max(255),
  }),
  category: 'content',
  label: '@vitnode/blog.notifications.post_published.label',
  description: '@vitnode/blog.notifications.post_published.description',
  subjectType: 'blog.post',
  defaults: { email: 'daily', inApp: true },
  email: true,
  access: async ({ c, data, userIds }) =>
    (await isPublished(c, data.postId)) ? userIds : [],
  present: ({ data, t }) => ({
    body: t('@vitnode/blog.notifications.post_published.body'),
    target: `/blog/${encodeURIComponent(data.slug)}`,
    title: t('@vitnode/blog.notifications.post_published.title', {
      title: data.title,
    }),
  }),
})
```

- **`access`** gives every recipient the same answer, so it checks once and
  returns all of `userIds` or none. Unpublish the article, and inbox items turn
  into placeholders and pending digests drop it.
- **`subjectType: "blog.post"`** - no plugin declares a `blog.post` subject, so
  core makes it mute-only. A reader can mute one article without unfollowing
  the category.
- **`defaults`** - in-app, plus a daily digest by email.

</Step>

<Step>

### Declare the subject readers follow

```ts title="plugins/blog/src/api/lib/notifications.ts"
export const blogCategorySubject = buildNotificationSubject({
  type: 'blog.category',
  canFollow: async ({ c, id }) => {
    const categoryId = Number(id)
    if (!Number.isSafeInteger(categoryId)) return false

    const [row] = await c
      .get('db')
      .select({ id: blog_categories.id })
      .from(blog_categories)
      .where(eq(blog_categories.id, categoryId))
      .limit(1)

    return !!row
  },
  resolveLabels: async ({ c, ids, locale }) => {
    const categoryIds = ids.map(Number).filter(Number.isSafeInteger)
    if (categoryIds.length === 0) return {}

    const rows = await c
      .get('db')
      .select({
        code: core_languages.code,
        id: categoryTranslations.itemId,
        name: categoryTranslations.name,
      })
      .from(categoryTranslations)
      .innerJoin(
        core_languages,
        eq(core_languages.id, categoryTranslations.languageId),
      )
      .where(inArray(categoryTranslations.itemId, categoryIds))

    const labels: Record<string, string> = {}
    for (const row of rows) {
      // The reader's language wins; any other translation is a fallback.
      if (row.code === locale || !(String(row.id) in labels)) {
        labels[String(row.id)] = row.name
      }
    }

    return labels
  },
})
```

`canFollow` only allows categories that exist. `resolveLabels` turns category
ids into names for the follow list on `/settings/notifications`, in the
reader's language, with one query for all ids.

</Step>

<Step>

### Publish from the Content Engine event

The blog runs on the [Content Engine](/docs/dev/content-engine), which emits
`content.blog.post.published`. A listener turns it into one notification for
the followers of every category the article is in. `loadPostSummary()` reads
the article's title and slug in its default language:

```ts title="plugins/blog/src/api/lib/notifications.ts"
export const notifyCategoryFollowersListener = buildEventListener({
  event: contentEventName(blogPostContentType.id, 'published'),
  name: 'notify-category-followers',
  handler: async (c, payload) => {
    const postId = payload.contentId
    const [summary, categories] = await Promise.all([
      loadPostSummary(c, postId),
      c
        .get('db')
        .select({ categoryId: blog_posts_category_id.relatedItemId })
        .from(blog_posts_category_id)
        .where(eq(blog_posts_category_id.itemId, postId))
        .orderBy(asc(blog_posts_category_id.position)),
    ])
    if (!summary || categories.length === 0) return

    await c.get('notifications').publish({
      type: postPublishedNotification,
      actorId: payload.scheduledBy ?? c.get('admin')?.user.id ?? null,
      followersOf: categories.map((row) => ({
        id: row.categoryId,
        type: 'blog.category',
      })),
      subject: { id: postId, type: 'blog.post' },
      data: { postId, slug: summary.slug, title: summary.title },
      idempotencyKey: `post-published:${postId}`,
    })
  },
})
```

It is registered on the top-level admin module:

```ts title="plugins/blog/src/api/modules/admin/admin.module.ts"
events: [...blogLegacyEventListeners, notifyCategoryFollowersListener],
```

- **`followersOf`** names up to 20 categories. A reader following two of them
  gets one notification. Core streams the followers, so a category with ten
  thousand of them still costs this listener one query.
- **`actorId`** is whoever pressed publish, or whoever booked the schedule. They
  are left out of their own announcement.
- **`idempotencyKey`** is per article. An article is announced once, like its
  `publishedAt` that records the first publication: unpublishing and publishing
  again, or a retried scheduled publish, does not notify anyone twice.

</Step>

<Step>

### Add the follow button

```tsx title="plugins/blog/src/pages/post-page.tsx"
import { FollowSubjectButton } from '@vitnode/core/tanstack/notifications'

// Rendered in the article header, under the title
const followCategory =
  item.categoryId[0] === undefined ? null : (
    <div className="flex flex-wrap items-center gap-3">
      <p className="text-muted-foreground text-sm leading-relaxed">
        {t('follow_category')}
      </p>
      <FollowSubjectButton
        subject={{ id: item.categoryId[0], type: 'blog.category' }}
      />
    </div>
  )
```

The article's `categoryId` list comes from the public content API. The button
follows the first category.

Guests see nothing. Signed-in readers get **Follow** and a mute toggle.

</Step>

## How durable is it?

<Callout type="warn" title="An interactive publish is announced best effort">
  The Content Engine emits events for interactive saves **after** its
  transaction commits. If the process crashes between that commit and the
  listener's `publish()`, that one announcement is skipped. The article itself
  is safe.
</Callout>

Scheduled publication runs in a durable queue task that retries until it
succeeds. It is **at least once**, so the listener can run twice - and the
idempotency key turns the second run into a no-op.

For producers you own, skip the gap entirely: call `publish()` with `tx` inside
the same transaction as your write. See
[Publish inside your transaction](/docs/dev/notifications/publishing#publish-inside-your-transaction).
