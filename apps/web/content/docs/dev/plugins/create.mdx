In this section we'll guide you through the process of creating your first VitNode plugin. Whether you're building a simple feature or a complex application, VitNode's plugin system has got you covered.

<Callout type="info" title="In a hurry?">
  [Create your first plugin](/docs/dev/tanstack/plugin) is the same thing in one
  page: scaffold, register, open the URL. This page is the longer version.
</Callout>

By creating a plugin, you can extend the functionality like:

- **🚀 APIs**: Build your own RESTful,
- **🧩 UI Components**: Create reusable components for your application,
- **📄 Pages and Layouts**: Define custom pages and layouts for your application,
- **⚡ Middleware**: Add custom middleware to handle requests and responses,
- **🗄️ Database Models**: Define your own database models and schemas,
- **🔗 Integrations**: Connect with third-party services and APIs.
- **⚙️ Custom Logic**: Implement any custom logic you need for your application.
- **🌟 And much more!**

### What you get

A plugin with one public page, already wired:

```txt
plugins/my-vitnode-plugin/
└── src/
    ├── config.tsx              registers the plugin with VitNode
    ├── locales/
    │   ├── en.json             the strings the page renders
    │   └── index.ts            the barrel config.tsx registers
    └── routes/
        ├── manifest.ts         declares one route at /my-vitnode-plugin
        └── home-page.tsx       what it renders
```

Add it to your app's `src/vitnode.config.ts` `plugins` array and the page is
live. There is nothing else to edit - no application route file, no generated
file. Read [Route Manifest](/docs/dev/plugins/route-manifest) for what those two
files in `routes/` can say.

<Callout title="Turborepo Only (Monorepo)" type="info">
  The generator adds your plugin to the workspace and to every package that
  depends on `@vitnode/core`, which is why it has to run from the monorepo root.
</Callout>

## Add Translations

VitNode is i18n-first: render user-facing text through translations rather than hardcoding it. Your plugin owns its languages and hands them to VitNode - apps never copy them.

```json title="plugins/{your_plugin}/src/locales/en.json"
{
  "{your_plugin}": {
    "hello": "Hello World"
  }
}
```

```ts title="plugins/{your_plugin}/src/locales/index.ts"
import type { LocaleMessagesMap } from "@vitnode/core/lib/i18n/types";

const messages: LocaleMessagesMap = {
  en: async () => await import("./en.json", { with: { type: "json" } }),
};

export default messages;
```

Register that barrel in `config.tsx` (`buildPlugin`) with `messages`, and your strings show up on the frontend.

<Callout title="Server strings live apart" type="info">
  If your plugin sends email, its server strings go in a second tree,
  `src/locales/api/`, registered with `buildApiPlugin` in `config.api.ts`. The
  API loads only that tree, so an API-only app never pulls in your UI copy. See
  [Server-side](/docs/dev/i18n/server).
</Callout>

Keys have to sit under your plugin's namespace, or they collide with core. The details are in [Namespaces](/docs/dev/i18n/namespaces) and [Server-side](/docs/dev/i18n/server).

## Where your pages live

Your pages stay in your package. A plugin's routes are read from
`routes/manifest.ts`, compiled into the app's generated route registry, and
imported straight out of your `dist` - nothing is copied into the application,
and there is no generated folder of your files to know about.

That means a page has exactly one home: the file you are editing is the file
that runs. See [Route Manifest](/docs/dev/plugins/route-manifest).
