## Pages

An AdminCP page is a route in `routes/manifest.ts` with `area: "admin"` and its
full `/admin/…` path. The page stays in your package, the application imports it
from your `dist`, and the navigation below is what puts it in the sidebar.

[AdminCP routes](/docs/dev/tanstack/admin) is the short guide and
[Route Manifest](/docs/dev/plugins/route-manifest#admincp-pages) the reference.
Like everywhere in VitNode, render text with translations - see
[Messages](/docs/dev/i18n/messages).

```ts title="plugins/{plugin_name}/src/routes/manifest.ts"
import type { PluginRouteDefinition } from "@vitnode/core/routing";

export const routes: PluginRouteDefinition[] = [
  {
    area: "admin", // [!code highlight]
    entry: "routes/admin-settings",
    id: "admin-settings",
    path: "/admin/blog/settings", // [!code highlight]
  },
];
```

```tsx title="plugins/{plugin_name}/src/routes/admin-settings.tsx"
import { useTranslations } from "use-intl";

const AdminSettingsPage = () => {
  const t = useTranslations("@vitnode/blog.admin.settings"); // [!code highlight]

  return (
    <div className="flex flex-col gap-2">
      <h1 className="text-2xl font-semibold tracking-tight">{t("title")}</h1>
      <p className="text-muted-foreground leading-relaxed">{t("desc")}</p>
    </div>
  );
};

export default AdminSettingsPage;
```

<Callout type="warn" title="The area chooses a shell, never a prefix">
  `area: "admin"` says which shell frames your page - the sidebar, the
  breadcrumb area, the admin session guard. It does **not** add `/admin` to your
  path, so write the path out in full.
</Callout>

<Callout>
  Pages in the AdminCP are automatically behind the admin session guard,
  whichever of the two ways they got there. That guard is a navigation rule: the
  API still has to check the staff permission itself. See [Staff
  permissions](/docs/dev/working-with-users/staff-permissions).
</Callout>

## Navigation items

To create own navigation items in the admin sidebar you can just create `nav` object inside `admin` in your plugin config.

<Steps>
<Step>

### Define items in config

As an example let's create a navigation item for blog categories:

```tsx title="plugins/{plugin_name}/src/plugin.tsx"
import { buildPlugin } from "@vitnode/core/lib/plugin";
import { SettingsIcon } from "lucide-react";

import { configPlugin } from "./config";

export const blogPlugin = () => {
  return buildPlugin({
    ...configPlugin,
    // [!code ++:9]
    admin: {
      nav: [
        {
          id: "settings",
          href: "/admin/blog/settings",
          icon: <SettingsIcon />,
        },
      ],
    },
  });
};
```

#### Nested Navigation

To create nested navigation items, you can use the `items` property:

```tsx title="plugins/{plugin_name}/src/plugin.tsx"
import { buildPlugin } from "@vitnode/core/lib/plugin";
import { ListIcon, SettingsIcon } from "lucide-react";
import { configPlugin } from "./config";

export const blogPlugin = () => {
  return buildPlugin({
    ...configPlugin,
    admin: {
      nav: [
        {
          id: "settings",
          href: "/admin/blog/settings",
          icon: <SettingsIcon />,
          // [!code ++:10]
          items: [
            {
              id: "general",
              href: "/admin/blog/settings/general",
            },
            {
              id: "seo",
              href: "/admin/blog/settings/seo",
            },
          ],
        },
      ],
    },
  });
};
```

#### Open in new tab

To open a navigation item in a new tab, you can use the `isOpenInNewTab` property:

```tsx title="plugins/{plugin_name}/src/plugin.tsx"
import { buildPlugin } from "@vitnode/core/lib/plugin";
import { SettingsIcon } from "lucide-react";
import { configPlugin } from "./config";
export const blogPlugin = () => {
  return buildPlugin({
    ...configPlugin,
    admin: {
      nav: [
        {
          id: "settings",
          href: "/admin/blog/settings",
          icon: <SettingsIcon />,
          isOpenInNewTab: true, // [!code ++]
        },
      ],
    },
  });
};
```

#### Gate by permission

To hide a navigation item from admins who lack a [staff permission](/docs/dev/working-with-users/staff-permissions), add a `permission`. It takes `{ module, permission }` - the `plugin` is inferred from your plugin, so you only reference the module and permission id you declared in `permissionStaff`:

```tsx title="plugins/{plugin_name}/src/plugin.tsx"
import { buildPlugin } from "@vitnode/core/lib/plugin";
import { ListIcon } from "lucide-react";
import { configPlugin } from "./config";

export const blogPlugin = () => {
  return buildPlugin({
    ...configPlugin,
    admin: {
      nav: [
        {
          id: "categories",
          href: "/admin/blog/categories",
          icon: <ListIcon />,
          // [!code ++]
          permission: { module: "categories", permission: "can_view" },
        },
      ],
    },
  });
};
```

The same `permission` field works on nested `items`. A parent item disappears once all of its children are hidden, and items without a `permission` are always shown.

<Callout type="warn">
  Hiding a nav item only hides the link - it does not protect the route. Guard
  the page itself and the underlying API too. See [Staff
  Permissions](/docs/dev/working-with-users/staff-permissions) for the full
  pattern.
</Callout>

</Step>
<Step>

### Add translation

VitNode automatically uses the `id` as translation key for the navigation item.

```json title="plugins/{plugin_name}/src/locales/en.json"
{
  "@vitnode/blog": {
    "title": "Blog",
    // [!code ++:5]
    "admin": {
      "nav": {
        "settings": "Settings"
      }
    }
  }
}
```

</Step>
  
</Steps>

## Keeping navigation out of the browser bundle

Your plugin config carries your content types - and the editor fields, form
layouts and table cells attached to them. The application's shell must not import
any of that just to draw a list of links: anything the shell imports is in the
browser bundle.

So the navigation half goes in a **browser-safe** module of its own, spread back
into your config, and one declaration feeds both:

```tsx title="plugins/{plugin_name}/src/admin/nav.tsx"
import type { AdminNavPluginSource } from "@vitnode/core/lib/plugin";

import { SettingsIcon } from "lucide-react";

import { blogPostContentType } from "@/content/post";
import { CONFIG_PLUGIN } from "@/const";

export const blogPostNav = {
  definition: blogPostContentType,
  icon: <SettingsIcon />,
};

export const adminNav = {
  pluginId: CONFIG_PLUGIN.pluginId,
  contentTypes: [blogPostNav],
  admin: {
    nav: [{ id: "settings", href: "/admin/blog/settings", icon: <SettingsIcon /> }],
  },
} satisfies AdminNavPluginSource;
```

```tsx title="plugins/{plugin_name}/src/config.tsx"
import { buildPlugin, contentTypeAdmin } from "@vitnode/core/lib/plugin";

import { adminNav, blogPostNav } from "./admin/nav"; // [!code highlight]
import messages from "./locales";

export const blogPlugin = () =>
  buildPlugin({
    ...adminNav, // [!code highlight]
    messages,
    contentTypes: [
      // Keep your field, column and form overrides here - only the definition
      // and the icon come from the nav module.
      contentTypeAdmin({ ...blogPostNav, forms: { layout: BlogPostForm } }),
    ],
  });
```

Nothing else to do. An app that installs your plugin discovers this module at
build time - it writes one literal import per configured plugin into
`src/admin-nav.gen.ts` - and works out which message namespaces your entries
need from the entries themselves.

<Callout type="warn" title="Keep it plain">
  `admin/nav` is imported by the browser bundle. Ids, hrefs, permissions, icons
  and content type definitions only. A screen, a form field or a table cell
  belongs in `config.tsx`, which is exactly what the split is for.
</Callout>

<Callout>
  A plugin that ships no `admin/nav` simply contributes no sidebar entries - it
  isn't an error.
</Callout>
