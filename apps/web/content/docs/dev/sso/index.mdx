VitNode has built-in OAuth2 single sign-on (SSO). Register an adapter in your API configuration, and a sign-in button for that provider appears on `/login` and `/register`. This page covers registering an adapter, the callback URL to give the provider, and how an SSO sign-in finds, links or creates an account.

## Quick start

Register an SSO adapter in `apps/api/src/vitnode.api.config.ts`:

```ts title="apps/api/src/vitnode.api.config.ts"
import { GoogleSSOApiPlugin } from "@vitnode/core/api/adapters/sso/google"
import { buildApiConfig } from "@vitnode/core/vitnode.config"

export const vitNodeApiConfig = buildApiConfig({
  // [!code ++:8]
  authorization: {
    ssoAdapters: [
      GoogleSSOApiPlugin({
        clientId: process.env.GOOGLE_CLIENT_ID,
        clientSecret: process.env.GOOGLE_CLIENT_SECRET,
      }),
    ],
  },
})
```

A **Google** button automatically renders on your login and registration forms,
four-color G included. [Google](/docs/dev/sso/google) shows where the client ID
and secret come from. The built-in adapters ship their own marks and colors, and
the Discord and Facebook buttons are filled with their brand color. A custom
adapter can [add its own](/docs/dev/sso/icons).

## On the login page

The provider buttons sit in their own column next to the email form, under one
**Continue with** heading, so each button only needs the provider's name (screen
readers still hear "Continue with Google"). On small screens the columns stack:
providers first, then the form.

- `/login` packs the providers into a two-column grid, so six of them take three
  rows instead of six. The passkey button goes right below.
- `/register` stacks them full width, because the sign-up form next to them is
  taller anyway.
- The method someone signed in with last - a provider, a passkey or a password -
  gets a **Last used** badge, and a last-used provider moves to the top of the
  grid. It's remembered in that browser only after a successful sign-in, so a
  visitor who gives up halfway through Discord's consent screen won't see it.
- Only one kind of method enabled? The card shrinks back to a single column.

## Callback URLs

When configuring OAuth2 applications in provider developer consoles, use the following redirect URI pattern:

```text
https://your-domain.com/login/sso/{provider_id}
```

For example: `https://your-domain.com/login/sso/google`. The domain is your
`VITNODE_WEB_URL`.

## The round trip

1. The sign-in button asks the API for the provider's authorization URL. The API
   creates a random `state` value, stores a salted hash of it in the
   `vitnode_auth--state-sso` cookie (named after `authorization.cookieName`),
   and sends the browser to the provider with the plain value.
2. The provider redirects back to `/login/sso/{provider_id}` with a `code` and
   the `state`.
3. The API checks `state` against the cookie and deletes the cookie. A missing
   or different value answers `400 Invalid state`, so a callback link someone
   else started cannot sign you in.
4. The adapter exchanges the `code` for a token, reads the provider account, and
   VitNode signs in, links or creates the account as described below.

The state cookie has no expiry date, so it never outlives the browser session.

## How accounts link

When a user signs in via SSO:
1. **Known identity.** The provider account was linked before, so the user is signed straight into it.
2. **Existing email match.** An account already uses that address. The visitor is asked for that account's password; once it checks out, the provider identity is linked to the account and they are signed in. From then on that provider signs them straight in (case 1). A social login can never take over an account on its own, because the password is what proves ownership.
3. **New visitor.** A new user is created with their social display name and email. Avatar and real name stay empty until the member imports them from [Connected accounts](/docs/dev/sso/connected-accounts).

Signed-in members can also connect more providers, import their avatar and name, and disconnect accounts in **Settings → Connected accounts**. See [Connected accounts](/docs/dev/sso/connected-accounts).

### SSO confirms the email

A provider only hands VitNode an address it has verified itself (the built-in
adapters refuse anything else), so a social sign-in doubles as email
confirmation:

- a **new visitor** starts out with `emailVerified: true`, even when an email
  adapter is configured and password sign-ups would have to confirm first;
- a **known identity** or a **freshly linked** account whose address is still
  unconfirmed is marked confirmed - provided the address the provider returned
  is the one on the account. An account whose email was changed since the link
  was made is left alone.

### Linking an existing account

The callback answers `409` with a short-lived, signed **link offer** - the
account's email, whether it has a password, and a token good for ten minutes.
The login page turns that into a "Connect *Provider* to your account" form: the
email is shown read-only, the visitor types their password, and
`POST /users/sso/{providerId}/link` verifies both before it writes the
`core_users_sso` row and mints a session. The token carries the provider account
id, so nothing about *which* identity gets linked is taken from the browser.

An account created by another provider has no password to confirm with. When an
email adapter is configured the form offers **Set a password** (the ordinary
reset flow) and asks them to try the provider again afterwards; without one it
points back to the login page.

Every successful link emits [`user.sso.linked`](/docs/dev/events/built-in-events).

The address the provider returns is matched in its canonical form, so a Google account that reports `jan.kowalski@gmail.com` finds the member who registered as `jankowalski@gmail.com` instead of quietly becoming a second account. See [One mailbox, one account](/docs/dev/advanced/auth#one-mailbox-one-account).
