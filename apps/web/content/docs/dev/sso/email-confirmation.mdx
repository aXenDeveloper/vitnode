Some providers never share an email address (Reddit, TikTok), share one without saying whether it is verified (Kick), or share one that is not always trustworthy (Microsoft, X without email access). VitNode still signs these people in: a returning member is recognised by their provider account, and a new visitor confirms an address of their own by opening an emailed link before any account exists - the same way password sign-ups [confirm their email](/docs/dev/email).

## When VitNode trusts a provider email

An adapter's `fetchUser` returns `email` and `emailVerified`. VitNode treats the address as **trusted** only when it is present and `emailVerified` is not `false`. Each built-in adapter sets `emailVerified` from the provider's own flag - for example `email_verified`, Microsoft's `xms_edov` or PayPal's `confirmed` - and the provider guides list which one.

A trusted email can create an account, match an existing account (which then needs its password before linking) and confirm an unconfirmed account. An untrusted email does none of these. It is only offered to the visitor as a suggestion.

## What the visitor sees

<Step>

### The provider sign-in finishes

The visitor signs in at the provider and lands on `/login/sso/{providerId}`. VitNode validates the round trip and asks the provider who they are.

</Step>

<Step>

### Returning members go straight in

If this provider account was linked before, the visitor is signed in. The email does not matter here, and an address stored earlier is kept even when the provider leaves it out this time.

</Step>

<Step>

### New visitors enter an email

Otherwise the page shows **Confirm your email**. The visitor types an address (pre-filled with the provider's unverified one, if there was any) and presses **Send confirmation link**. VitNode answers the same way whether or not the address has an account.

</Step>

<Step>

### They open the link in the same browser

The page switches to **Check your email**, with **Send a new link** and **Use a different email** if the message does not arrive. The visitor opens the link from the email, `/login/sso/{providerId}?confirm=...`, in the same browser. Then one of two things happens:

- **The address is new** - VitNode creates the account with `emailVerified: true`, links the provider account and signs the visitor in.
- **The address belongs to an account** - the page shows **Connect _Provider_ to your account** and asks for that account's password, exactly like a provider email that matches an account.

## Why the link only works in the same browser

Without that rule, someone could sign in with **their own** Reddit account, type **your** address, and wait for you to click the link out of curiosity. That would create an account under your email that their Reddit account can sign in to.

So the pending sign-in is tied to the browser that started it through an HttpOnly cookie, and the link only finishes it there. Opened anywhere else - another browser, or a phone - the page says **Open the link where you signed in** and signs nobody in.

## Security rules

- The pending sign-in lives on the server, in `core_sso_pending`. The browser holds only a random token in an HttpOnly cookie, and the database stores only hashes of that token and of the link's. Provider tokens are never stored.
- A link works for 30 minutes and once. Sending a new link replaces the old one. The visitor can ask for one every 30 seconds, up to five times.
- VitNode never makes up an address from a username, never marks a provider email verified just because OAuth succeeded, and never links accounts by an unverified email.

## Requirements

Confirmation needs an [email adapter](/docs/dev/email). Without one, VitNode cannot send the link: a new visitor from such a provider sees **We need a verified email**, and the callback answers `422 { "error": "email_unavailable" }`. Returning members are not affected.

## API

| Method | Path                                      | Body        | Answers                                                                                       |
| ------ | ----------------------------------------- | ----------- | --------------------------------------------------------------------------------------------- |
| `GET`  | `/users/sso/{providerId}/callback`        | -           | `202 { emailRequired: true, email }` when an address must be confirmed                       |
| `POST` | `/users/sso/pending/{providerId}/email`   | `{ email }` | `201`, `400 invalid_pending`, `429 too_many_emails`                                           |
| `POST` | `/users/sso/pending/{providerId}/confirm` | `{ token }` | `200 { id }` signed in, `409` link offer, `400 invalid_pending` (other browser) or `invalid_link` |

The email uses the `core.auth.sso_confirm_email.email` translations, so it follows the visitor's language.
